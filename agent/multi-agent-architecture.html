多 Agent 什么时候值得用：单 Agent、固定 Workflow、多 Agent 的一次成本实测

Loong2026/10/13AgentAI Agent多 AgentWorkflow成本大约 9 分钟约 2635 字

环境：Windows 11、OpenJDK 11.0.32.1（Temurin），纯 JDK 单文件实验，无第三方依赖
说明：本实验用带计量的 MockLLM 测量两种硬指标——LLM 调用次数和累计字符量（输入+输出，作为 token 消耗的代理指标）。它测量的是三种架构的成本结构，不测量回答质量；质量对比需要真实模型加评测集，是另一个实验。字符量的比例关系成立，绝对值不代表真实账单。

问题：多 Agent 很火，但"什么时候值得用"很少有数字

2025 年以来，"多 Agent 系统"成了 Agent 方向最热的话题之一，各种编排框架都在推多 Agent 能力。但我在选型时翻了很多资料，发现绝大多数文章停在"多 Agent 更强大"的定性描述，很少有人把三种形态放在一起算成本账：

  • 单 Agent：一个模型、一个上下文，串行做完所有事。
  • 固定 Workflow：流程写死在代码里，模型只在每个节点里干活，没有决策权。
  • 多 Agent：一个编排者动态拆解任务，多个工人 Agent 各自在独立上下文里执行，再汇总。

Anthropic 的工程博客《Building effective agents》里有一个著名观点：能用单 Agent 解决的就不要用多 Agent，能用固定流程的就不要让模型自由发挥。我认同这个方向，但"认同"不是证据。所以我写了一个带计量的实验，把三种架构跑在同一组任务上，看调用次数和 token 消耗（用字符量做代理）的实际差异。

先把实测结论放这：

  1. 任务形状固定时，Workflow 全面最便宜——它没有一次调用花在"决定干什么"上。
  2. 单 Agent 的成本随步数膨胀：每一步都要背着全部历史跑，子任务越多，上下文税越重。
  3. 多 Agent 只在一种情况下回本：任务的拆解方式事先不知道，或者子任务数量会动态变化。这时候 Workflow 直接漏做，单 Agent 上下文膨胀到最贵，多 Agent 的协调开销反而显得便宜。

实验设计：三种架构、三个任务、两个指标

实验用 MockLLM，但每次调用都计量：调用次数 +1，输入输出字符累加。三种架构的核心差异在上下文管理方式，代码骨架如下（完整实现见文末说明）：

// 单 Agent：历史不断累积，每一步都携带全部过去
for (String st : subtasks) {
    String out = m.call(ctx.toString(), research(st));   // ctx 每轮变长
    ctx.append("已完成[").append(st).append("] 结果:").append(out).append("\n");
}

// 固定 Workflow：每个子任务独立最小上下文，流程写死
for (int i = 0; i < slots; i++) {
    results.add(m.call("执行子任务:" + subtasks.get(i), research(subtasks.get(i))));
}

// 多 Agent：编排者先拆解（一次调用），工人各自独立上下文，编排者再汇总
String plan = m.call(orchestratorCtx.toString(), "拆解为 N 个子任务");
for (String st : subtasks) {
    results.add(m.call("你是工人 Agent，只负责:" + st, research(st)));
}
m.call(orchestratorCtx.toString(), "综合结论");           // 编排者上下文含全部汇报

三个任务按"拆解是否事先可知"设计梯度：

任务子任务数特点
T1 翻译一句话1不需要拆解
T2 对比两个框架2拆解固定且已知
T3 给三个微服务写发布清单3模拟"流程设计时按 2 个槽位写死，实际来了 3 个子任务"

实测结果：T1 单步任务

===== T1 简单任务：翻译一句话 =====
子任务数: 1，固定 workflow 槽位: 1
单 Agent     | LLM调用 2 次 | 累计字符 172 | 结果完整
固定 Workflow | LLM调用 2 次 | 累计字符 111 | 结果完整 | 零决策开销
多 Agent     | LLM调用 3 次 | 累计字符 227 | 结果完整 | 协调开销 = 拆解+汇总 2 次编排调用

单步任务上，多 Agent 的协调开销暴露无遗：一次拆解调用、一次汇总调用，什么都没干就先多了两次模型调用，字符消耗是 Workflow 的两倍。这就是"能用单 Agent 就不用多 Agent"的量化形态——对简单任务，多 Agent 是纯粹的负资产。

实测结果：T2 双子任务调研

===== T2 中等任务：两个框架对比调研 =====
子任务数: 2，固定 workflow 槽位: 2
单 Agent     | LLM调用 3 次 | 累计字符 468 | 结果完整 | 上下文逐轮膨胀
固定 Workflow | LLM调用 3 次 | 累计字符 283 | 结果完整 | 零决策开销
多 Agent     | LLM调用 4 次 | 累计字符 504 | 结果完整

注意单 Agent 的字符量（468）已经明显超过 Workflow（283）：调用次数相同，但单 Agent 第二步的输入里带着第一步的完整结果，第三步（汇总）又带着全部历史。调用次数相同，token 消耗可以差出 60% 以上——上下文长度才是账单的大头，不是调用次数。

多 Agent 仍然最贵（504）：拆解和汇总两次编排调用，在这个任务形状下没有产生任何价值，因为拆解方式本来就写死在 Workflow 里也行。

实测结果：T3 计划外子任务，Workflow 漏做了

===== T3 复杂任务：三个服务的发布检查（workflow 只有 2 个槽位） =====
子任务数: 3，固定 workflow 槽位: 2
单 Agent     | LLM调用 4 次 | 累计字符 627 | 结果完整
固定 Workflow | LLM调用 3 次 | 累计字符 227 | 结果不完整 | 流程只有 2 个槽位，漏做 1 个子任务
多 Agent     | LLM调用 5 次 | 累计字符 541 | 结果完整 | 动态拆解 3 个子任务

这是唯一一个多 Agent 回本的任务，而且同时暴露了另外两家的弱点：

  • Workflow 漏做了。流程按 2 个槽位设计，来了 3 个子任务，第 3 个直接被丢弃，而且它"不知道自己不知道"——输出看起来完整，实则缺了一块。固定流程的脆弱性就在这：任务形状变了，系统不会报错，只会静默给出不完整的答案。
  • 单 Agent 的上下文税到了最高点。627 字符，三种架构里最高。子任务从 2 个变 3 个，Workflow 的字符量涨了不到一倍，单 Agent 的累积上下文却带着全部历史越滚越大。
  • 多 Agent 541 字符，第一次比单 Agent 便宜。原因：工人各自用独立的最小上下文，只有编排者背全局历史。子任务之间不需要互相看到对方的过程时，这种隔离直接省钱。

数据说明了什么

把三个任务摆在一起，成本结构的分野很清楚：

架构钱花在哪优势场景死穴
单 Agent上下文逐轮膨胀步数少、步骤间强依赖的任务长链条任务的 token 税
固定 Workflow零决策开销，每步最小上下文形状固定、可枚举的流程任务形状变化时静默漏做
多 Agent拆解 + 汇总的固定协调税拆解动态、子任务独立的任务简单任务上纯亏

多 Agent 的回本条件可以写成一个不等式：动态拆解的收益 + 上下文隔离省的钱 > 拆解和汇总的协调税。T1、T2 不满足，T3 满足。这个不等式比"多 Agent 更强大"之类的定性话术有用得多——拿到一个新需求，先问"拆解方式事先知道吗、子任务之间需要互相看见吗"，答案直接指向架构。

这个实验没测什么

诚实地说，这个实验只测了成本结构，没测质量：

  • 质量维度是 MockLLM 测不了的。多 Agent 的支持者常说分工带来质量提升（专门的调研 Agent、专门的审稿 Agent）。这可能是真的，但验证它需要真实模型、固定评测集和盲评，是另一个量级的实验。本文不做这个声明。
  • 失败传播没模拟。真实多 Agent 系统里，一个工人出错，编排者未必能发现；错误的中间结果会污染汇总。这个风险在 Mock 里不存在。
  • 延迟没测。多 Agent 的工人可以并行（本文实现是串行的），实际延迟可能低于单 Agent——这是多 Agent 的另一个潜在收益，但受 API 限速影响，不好一概而论。

所以本文的结论应读作"成本结构上的选型依据"，不是"多 Agent 不值得研究"。

选型决策清单

拿到一个 Agent 需求，按这个顺序过一遍：

  1. 单个模型调用加工具能完成吗？能，就到这为止。大多数"Agent 需求"其实是 function calling 需求。
  2. 流程能画成固定的 DAG 吗？能，用 Workflow 实现，把模型限制在节点里。流程图就是你最好的调试工具。
  3. 拆解方式必须运行时决定吗？子任务之间互相独立吗？两个都是"是"，多 Agent 的协调税才花得值。
  4. 无论选哪个，加上一层护栏：最大步数、错误熔断、成本上限——这在三种架构里都是必需品，和选型无关。

小结

  • 三种架构的成本差异主要来自上下文管理方式和协调开销，不是来自"智能程度"。
  • Workflow 在任务形状固定时全面最便宜，但任务形状一变会静默漏做，监控它的完整率。
  • 单 Agent 为简单和强依赖场景保留，长链条任务警惕上下文税。
  • 多 Agent 的回本条件：拆解动态 + 子任务独立。不满足这两个条件，协调税就是纯成本。
  • 成本可以本地模拟，质量必须用真实模型评测——别把这两个实验混成一个结论。
