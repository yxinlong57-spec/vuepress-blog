## 三个词经常被混用，先看它们在问什么

面试和日常排查里，"穿透、击穿、雪崩"经常被当成同一件事。它们其实在问三个不同的问题：

- **穿透**：请求的数据在缓存里没有，在数据库里也没有。每次请求都要走一遍"缓存 miss → 查库 → 空手而归"，缓存等于没起作用。
- **击穿**：某个被高频访问的热点 key 刚好失效，失效瞬间大量并发请求一起回源。
- **雪崩**：一大批 key 在几乎同一时刻失效，回源从"一个点"变成"一大片"。

区别可以压成一句话：**穿透是"数据不存在"，击穿是"一个热点 key 不存在于缓存中"，雪崩是"很多 key 同时不在缓存中"。** 成因不同，防护方向也不同——空值缓存治穿透、互斥重建治击穿、TTL 抖动治雪崩。用错了方向，花的力气全白费。

下面用一个纯 JDK 实验把三种场景和三种防护都跑一遍，用数字看效果。

## 实验设计：一个会计数的"假数据库"

真实环境复现这三类问题，需要 Redis + 数据库，还要卡准并发时机，不好复现。我把两侧都换成可控的替身：

- `Db` 用一个 `ConcurrentHashMap` 存数据，每次查询固定 `sleep(50)` 毫秒模拟慢查询，同时记录**累计调用次数**和**同时在飞的查询数峰值**。
- `cache` 直接用 `ConcurrentHashMap` 代替 Redis，这里只关心"命中 / 未命中 / 回源"这层逻辑。
- 让并发"同时到达"用 `runConcurrent`：`CountDownLatch` 把 n 个线程压到同一起跑线再放行；需要错峰时用 `runStaggered`，第 i 个任务延迟 `i*gap` 毫秒再发。

只统计两个量：**DB 被调用了多少次**、**DB 的瞬时并发峰值多高**。前者衡量"白干活"，后者衡量"数据库扛不扛得住"。

## 缓存穿透：查的是数据库里根本没有的数据

场景：反复查询一个数据库里不存在的用户 `user:999`，共 100 次请求。

```java
for (int i = 0; i < 100; i++) {
    String key = "user:999";
    if (!cache.containsKey(key)) {
        String v = db.query(key);          // 每次都走这里
        if (v != null) cache.put(key, v);  // 查不到就不写缓存
    }
}
```

实测输出：

```text
不缓存空值：100 次请求 -> DB 调用 100 次
```

100 次请求全部打到数据库。因为查询结果为空时没有写缓存，下一次请求还是 miss，缓存形同虚设。

修法是**把"空结果"也缓存起来**，用一个哨兵值表示"数据库确实没有"：

```java
if (!cache.containsKey(key)) {
    String v = db.query(key);
    cache.put(key, v == null ? "NULL_SENTINEL" : v);   // 空值也写进缓存
}
```

```text
缓存空值：100 次请求 -> DB 调用 1 次 (其余命中空值哨兵)
```

100 次降到 1 次。空值缓存必须配一个**较短的 TTL**（比如 60 秒），否则数据后来真的写进去了，缓存里的"空"会一直骗人。加一个短的过期兜底，既挡住重复的穿透，又不会长期读到脏的"不存在"。

如果恶意请求每次都换不同的 key，空值缓存会被撑爆，这时要在前面加**布隆过滤器**：把库里存在的 key 预先放进过滤器，请求先过它，判定"一定不存在"的直接返回。布隆过滤器只会把不存在误判成存在（假阳性），不会漏判，所以用它挡不存在的 key 是安全的；代价是它本身有误判率，必须配合空值缓存一起用，不能单靠它。

## 缓存击穿：一个热点 key 失效的瞬间

场景：热点 key `hot:100` 的缓存刚好过期，50 个并发请求同时到达。

```java
runConcurrent(50, i -> {
    String key = "hot:100";
    String v = cache.get(key);
    if (v == null) {              // 50 个线程几乎同时判断为 miss
        v = db.query(key);
        cache.put(key, v);
    }
});
```

```text
无互斥锁：50 并发 -> DB 调用 50 次, DB 并发峰值 50
```

50 个并发请求全部回源——它们几乎同时判断缓存为空，谁也没等谁。热点 key 本来的 QPS 就高，这一下就是 50 倍的瞬时压力。

修法是**只让一个线程去重建缓存，其余等它**：

```java
if (v == null) {
    synchronized (locks.computeIfAbsent(key, k -> new Object())) {
        v = cache.get(key);        // 双重检查，前一个线程可能已经填好了
        if (v == null) { v = db.query(key); cache.put(key, v); }
    }
}
```

```text
互斥锁+双重检查：50 并发 -> DB 调用 1 次, DB 并发峰值 1
```

50 降到 1。**双重检查不能省**：拿到锁的时候缓存可能已经被前一个线程写好了，再查一次才避免重复回源。

本机单实例里 `synchronized` 够用；多实例部署要换成 Redis 分布式锁（`SET key value NX EX`）。另一种更省心的思路是**逻辑过期**：缓存里存"数据 + 逻辑过期时间"，物理上永不过期，值到点了由后台异步线程更新，读请求一律读旧值。它牺牲一点实时性，换来的是完全没有回源尖峰。

## 缓存雪崩：一批 key 同时失效

场景：200 个 `sku:i` 的 key 设置了相同的过期时间。

```text
统一过期：200 key 同时失效 -> DB 调用 200 次, DB 并发峰值 200
```

200 个 key 在同一秒失效，紧接着 200 个请求同时回源，数据库瞬时并发冲到 200。击穿是"一个点"，雪崩是"一整个面"。

雪崩最常见的成因就是**设 TTL 时用了一个固定值**，批量写入让所有 key 过期时间一样。核心修法是**把过期时间打散**：

```java
// 原本写死 3600，改成
cache.put(key, v, 3600 + random.nextInt(600));   // 3600~4200 秒之间随机
```

再配合请求错峰，实测：

```text
TTL 抖动+错峰：200 key -> DB 调用 200 次, DB 并发峰值 4
```

注意这里**总调用次数还是 200**：抖动不会减少需要回源的 key 数量，它压下去的是**瞬时并发峰值**（200 降到 4）。雪崩要防的是"数据库被瞬间打垮"，不是"总工作量变大变小"。

雪崩还有几个兜底手段：**多级缓存**（本地 Caffeine + Redis，Redis 挂了本地还能顶一下）、**降级与限流**（回源量超阈值就返回默认值或排队，宁可少量请求失败也不让库挂掉）、**缓存预热**（重启或批量写后，先把热点数据加载进来）、以及 Redis 本身的高可用（哨兵 / 集群），避免"整个缓存服务挂掉"这种更大号的雪崩。

## 三者对照与防护选择

| 问题 | 触发条件 | 表现 | 主要防护 | 兜底 |
| --- | --- | --- | --- | --- |
| 穿透 | 数据在缓存和库里都不存在 | 每次请求都回源 | 空值缓存 + 布隆过滤器 | 参数校验、限流 |
| 击穿 | 单个热点 key 失效的瞬间 | 一个点上的并发回源 | 互斥重建 / 逻辑过期 | 二级缓存 |
| 雪崩 | 大批 key 几乎同时失效 | 一大片并发回源 | TTL 随机抖动 | 多级缓存、降级、预热 |

判断顺序：先看是"不存在"还是"过期"，再看影响范围是"一个"还是"一批"。

## 这些数字的边界

- 实验用 `ConcurrentHashMap` 代替 Redis、用固定 `sleep` 代替数据库，测的是**逻辑差异**，不是真实 Redis 的吞吐。真实环境下 `synchronized` 只锁住单实例，多实例要用分布式锁；布隆过滤器的容量和误判率要按数据量重新算。
- 空值缓存的 TTL 设多短，取决于业务的"写后多久会被读到"。设太短挡不住穿透，太长会让新数据读不到。
- 逻辑过期牺牲了读一致性，用之前要想清楚业务能否接受读到旧值。
- `runConcurrent` 保证的是"尽量同时开始"，Windows 本机的线程调度仍有抖动，峰值数字看趋势，不当精确基准。

## 小结

- 穿透是"数据不存在"，防护靠空值缓存和布隆过滤器，100 次请求从打到库 100 次降到 1 次。
- 击穿是"一个热点 key 失效"，防护靠互斥重建或逻辑过期，50 并发从回源 50 次降到 1 次。
- 雪崩是"一批 key 同时失效"，防护靠 TTL 随机抖动，总回源量不变，但并发峰值从 200 压到 4。
- 三者成因不同，防护不能互相替代；先在代码里分清当前命中的是哪一类，再选对应的手段。
