## 快速认识

黑马头条可以写进简历，但招聘方通常一眼就能看出它是公开课程项目。把项目名写成“某新闻资讯平台”，再配一句“负责整体架构设计”，面试官大概率会提高警惕。不是因为课程项目不能写，而是这句话通常超出了个人复现项目的真实边界。

更稳的写法是明确标成个人实践项目，然后抓住一条真正跑通过的链路：自媒体文章发布、审核状态流转、搜索索引同步，以及服务之间的远程调用。项目里真正有价值的不是十几个模块名，而是你能不能解释一条消息为什么可能重复、搜索为什么可能落后、服务超时后业务状态会变成什么样。

项目名可以写“内容社区后端（个人实践项目）”或“微服务内容平台后端（课程复现）”，面试时直接说明基于公开课程资料完成复现。技术栈只留自己核对过的版本，职责只写能拿出配置、日志、测试或代码解释的部分。

如果你现在只想要一份能修改的模板，可以直接看文末。完整版适合已经跑通两三条核心链路的人，轻量版适合项目经历只能占一页简历的一小部分。模板里的方括号不是装饰，它们提醒你别把公开仓库的能力直接当成自己的经历。

## 拓展

### 项目定位先说清楚

“黑马头条”适合出现在文章标题和学习记录里，不适合原样放在简历项目名中。简历要给招聘方一个业务识别点，比如“内容社区后端”“新闻资讯平台后端”，同时保留项目性质，比如“个人实践”或“课程复现”。

不建议写成：

```text
黑马头条新闻资讯平台 | 2024.03 - 2024.09
负责整个微服务架构设计、服务拆分、线上部署和性能优化。
```

这里的问题不在于项目来源，而在于把课程复现写成了个人主导的企业平台。没有代码所有权、设计文档、监控和线上数据，追问两轮就容易接不上。

更可信的表达是：

```text
内容社区后端（个人实践项目）
基于公开课程资料完成复现，重点跑通文章发布、异步审核、搜索索引同步
和远程调用失败排查链路，并通过日志、数据库记录和测试验证状态变化。
```

如果只是看了课程、没有完整跑过，应该写“学习项目”或“课程练习”，不要写“项目开发”。时间范围也按自己的实际复现时间填写，不要照搬公开仓库的演示周期。

### 技术栈要和实际工作对应

公开仓库里能看到 Java 8、Spring Boot 2.3.9、Spring Cloud Hoxton.SR8、Nacos、Gateway、OpenFeign、Ribbon、Hystrix、MyBatis-Plus、MySQL、Redis、MongoDB、Elasticsearch、RabbitMQ、xxl-job 和 Seata 1.4.2。简历里出现这些名字不算错，前提是你能在自己的工程里找到对应依赖和运行痕迹。

| 简历中写到的内容 | 至少要能拿出什么 |
| --- | --- |
| Spring Boot、Spring Cloud 版本 | 自己的 `pom.xml` 或依赖树 |
| Nacos、Gateway | 服务注册记录、路由配置或请求日志 |
| OpenFeign、Ribbon、Hystrix | 调用配置、超时日志或降级结果 |
| RabbitMQ | 发送记录、消费日志、重复投递测试 |
| Elasticsearch | 索引映射、查询语句或同步记录 |
| Redis | 具体 Key、过期策略和一次缓存问题 |
| Seata、xxl-job | 实际配置、运行记录和事务或任务链路 |

技术栈不是越长越好。写了 Seata，却只会背“AT 模式解决分布式事务”；写了 Redis，却说不清缓存哪个 Key、什么时候删、删除失败怎么办，这些内容反而会变成面试中的风险点。

### 四条职责线比八个模块名更有用

简历篇幅有限，不需要把 admin、article、behavior、comment、data-sync、search、user、wemedia 平均写一遍。可以围绕下面四条能力线组织：

| 能力线 | 简历动作 | 面试证据 |
| --- | --- | --- |
| 服务协作 | 梳理 Nacos、Gateway、OpenFeign 的调用关系并排查调用失败 | 路由配置、服务日志、异常堆栈 |
| 异步审核 | 用 RabbitMQ 解耦文章发布和审核任务 | 消息发送、消费、重试和重复投递记录 |
| 搜索同步 | 维护文章索引字段，处理 MySQL 与 Elasticsearch 差异 | 索引映射、同步任务、数量比对脚本 |
| 一致性防守 | 用业务唯一键、状态机、重试和补偿处理重复与失败 | 重复消费测试、状态变化记录 |

Redis、Seata、xxl-job 可以写，但要放在具体问题里。单独写“使用 Redis、Seata、xxl-job”，信息量很低，面试官也无法判断你是配置过、演示过，还是真正处理过故障。

### 为什么审核要异步

面试官常从一句话开始问：

> 为什么文章审核要异步，直接同步调用不行吗？

回答不要只背“提高系统吞吐量”。先把链路说具体：发布接口写入文章数据后，需要把审核任务交给别的服务或第三方能力；审核结果还会影响文章状态和 App 端可见性。同步等待会占用请求线程，第三方超时也会把发布接口拖慢。

可以这样回答：

> 审核可能依赖外部接口，耗时和失败率都比普通数据库写入高。同步等待会占用请求线程，也容易让发布接口超时。我把审核任务通过 RabbitMQ 解耦，同时处理消息可靠性、重复消费、审核状态回滚和用户查询延迟。项目里能验证的是本地或测试环境下的链路，我不会把它说成生产流量。

接下来大概率会问消息重复。这里不要先堆“手动 ACK”“死信队列”这些名词，先把状态说清楚：

```text
同一个文章 ID + 审核事件类型只允许完成一次有效状态流转。
消费前检查事件唯一键和当前文章状态。
已经审核完成的文章再次收到相同消息时，直接记录并返回，不重复修改状态。
消费失败时不确认消息，交由重试或补偿处理。
```

这段回答能带出幂等、状态机和失败重试。比背“RabbitMQ 可靠投递三件套”更接近真实开发，也更容易继续追问。

### 搜索同步不能只写“保证一致”

最容易露怯的一句话是：“使用 RabbitMQ 同步 Elasticsearch，保证数据一致。”

消息可能丢，也可能重复；索引还可能因为分词、字段映射或同步延迟而查不到。更可信的写法是把同步拆成触发、消费、比对和修复：

```text
文章状态变更
-> 发送审核或同步消息
-> 消费端更新 Elasticsearch
-> 记录消息唯一键和消费状态
-> 定时核对 MySQL 与索引文档数量及关键字段
-> 差异数据重新投递或全量修复
```

对应到简历里，应该出现“消息唯一键”“消费幂等”“失败重试”“索引比对”“差异修复”这些动作。只写“使用 Elasticsearch 做全文检索”太浅，只写“使用消息队列保证最终一致”又太笼统。

如果面试官问“为什么不用双写”，可以回答：双写把 MySQL 和 Elasticsearch 放进了同一个业务请求。数据库成功、搜索失败时仍然不一致。消息或定时任务只是把失败延后处理，不能省略重试、幂等和比对。

### Redis、Seata 和 Feign 的边界

这三个组件很容易被写成“用过就加分”，实际面试更关心边界。

**Redis。** 审核状态属于关键业务状态，数据库最终状态优先。缓存更新要围绕具体键设计过期、删除和重建策略。不要笼统写“保证缓存一致性”。如果做过热点文章缓存，就说清楚缓存了哪些字段、空值缓存设多久、删除失败怎么重试。

**Seata。** 黑马头条里有 Seata，但不代表每个跨服务调用都应该塞进分布式事务。至少要能区分哪些表必须在同一个本地事务里更新，哪些动作允许异步，哪些失败需要业务补偿。如果只是复现示例，就写“分析跨服务事务边界”，不要写“实现生产级分布式事务”。

**Feign。** 调用失败后先区分读接口和写接口。读接口可以返回缓存、默认值或降级结果；写接口不能随便重试，要确认幂等条件。超时、熔断和重试参数都要有依据。简历里写“处理远程调用失败”，背后至少要有一次日志、异常堆栈或配置记录。

### 面试官最容易追问的六件事

#### 1. 文章审核消息重复怎么办

用业务唯一键和状态机。重复消息只能留下消费记录，不能再次改变审核状态。面试时要说清楚唯一键是什么、状态从哪里流转到哪里、重复消息返回什么。

#### 2. 搜索索引为什么不用双写

双写会扩大请求失败范围。数据库提交成功、搜索更新失败时，业务状态和索引仍然不一致。消息或定时任务只能提供重试入口，最后还要有幂等和差异修复。

#### 3. 项目有没有线上数据

没有就明确说没有。这是课程复现项目，测试环境和构造数据都可以讲，但不能把公开仓库 README 中的团队规模、开发周期和业务数字抄进个人经历。

#### 4. Seata 解决了哪些问题

先说事务发起方、参与方、回滚条件和锁等待成本。如果只是复现了一个 AT 模式示例，就诚实写“用于分析跨服务事务边界”，不要把它说成所有一致性问题都已解决。

#### 5. Redis 缓存和审核状态怎么保持一致

不要承诺强一致。审核状态以数据库最终状态为准，缓存只服务具体读取场景。需要回答缓存过期、删除失败、并发重建时分别怎么处理。

#### 6. 项目里到底做成了什么

准备一条能完整讲出来的链路，比罗列八个服务更有效。比如从文章提交、发送审核消息、消费结果、更新状态，到搜索索引生成和异常补偿，能画出调用关系并指出失败点，项目就有了可追问的内容。

### 七天补强清单

想把这个项目写得更有底气，可以按下面顺序补证据：

1. 画一张只包含文章发布、审核、搜索同步的调用图。
2. 为审核消息增加唯一键，构造同一消息重复投递，记录状态变化。
3. 查一次 MySQL 文章表和 Elasticsearch 文档数量，保存差异原因。
4. 停掉 search 服务，观察 Gateway 或调用方的错误，保存日志。
5. 对热点文章读取补一次缓存穿透或热点 Key 重建实验。
6. 在自己的仓库中记录启动顺序、依赖版本和接口示例，删除课程宣传数据。
7. 准备三个问题：为什么用消息、为什么不用双写、失败后怎么恢复。

### 投递前再检查一次

简历上的每一句都应该能回答三个问题：我改了什么，怎么验证，失败时怎么办。回答不了，就删掉或改成更小的动作。

项目名、时间和版本号要和其他材料一致。Git 提交、运行日志、测试记录、截图和 README 能支撑到什么程度，简历就写到什么程度。没有任何真实数据时，不补 QPS、用户量、响应时间和“提升百分之多少”。

如果对方追问项目来源，直接说“基于公开课程资料完成的个人实践项目”。这不是减分项。真正减分的是把公开课程项目说成自己主导的大厂系统，却解释不了代码和状态流转。

### 总结

黑马头条值得写，前提是把它当成一次微服务链路实践，不要当成虚构的企业履历。

简历里保留一条能讲透的异步审核和搜索同步链路，比把八个服务全部写成“负责”更有说服力。如果让我改这份简历，我会删掉“架构设计”“全栈负责”和所有线上数据，只留下文章状态流转、消息幂等、索引比对和远程调用排查。

面试官能顺着这四件事继续问，你才有机会展示真正的技术能力。
