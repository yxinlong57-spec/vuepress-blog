## 先说结论

一份 Java 后端简历最重要的不是把自己写得像架构师，而是让招聘方在几十秒内看到三件事：你投什么岗位、你做过什么真实链路、这些链路能不能继续追问。

项目经历不要只列技术栈。更有效的写法是“业务动作 + 技术机制 + 约束条件 + 可验证结果”。例如“用 Redis 缓存商品数据”只说明使用过 Redis；“针对热点商品使用 Cache Aside、空值缓存和互斥重建，记录缓存失效时的数据库查询和最终恢复结果”才能让面试官知道你真的处理过问题。

下面是我写的一份草稿简历，供大家参考。身份和教育信息使用示例值，项目部分结合了公开课程项目和常见校招项目结构；投递时替换身份信息，并只保留自己确实运行、修改和验证过的内容。

## 好简历遵循什么标准

Harvard 的职业中心把简历概括为一份针对岗位的营销文档：内容要简洁、具体、事实导向，招聘者会快速扫描；每条经历要用动作动词和结果说明，不用第一人称叙述。MIT CAPD 的简历指南也强调，内容要根据职位选择，格式保持一致，项目要说明技术和上下文，招聘者只会花很短时间看最相关的信息。

这份草稿按下面的顺序组织：

| 模块 | 回答的问题 | 写作要求 |
| --- | --- | --- |
| 求职意向 | 你想投什么 | 一句话写明岗位和类型 |
| 教育背景 | 你是否符合基本门槛 | 学校、专业、学历、时间、相关课程 |
| 专业技能 | 你具备哪些工具能力 | 分组写，不把名词堆成一行 |
| 项目经历 | 你做过什么 | 业务链路、技术动作、失败处理和验证结果 |
| 技术记录 | 你能否持续输出 | 只放有内容的仓库或文章 |

校招和实习简历通常控制在一页。字号不要低于 10pt，页边距至少半英寸，项目间格式统一。照片、年龄、性别、婚育状态一般不需要出现在技术简历里。

### 技能不能写成名词仓库

下面这行信息量很低：

```text
Java、MySQL、Redis、Spring、Spring Cloud、RabbitMQ、Docker、Linux、Git
```

更好的方式是按类别说明熟悉程度和场景：

```text
MySQL：理解索引、事务和锁，能使用 Explain 分析慢 SQL；
Redis：使用过 Cache Aside、Lua、Redisson 和 Stream 消费组；
RabbitMQ：处理过发送确认、消费确认、重试和幂等。
```

如果只是看过课程、没有在项目里用过，不要写成“熟练”。可以用“了解”“学习过”或干脆放到正在学习的方向里。面试官不会因为你少写一个名词扣分，却会因为一句“精通”问到项目细节。

### 项目经历要有主次

简历上的项目不要平均分配。最相关、最能讲深的放前面。电商项目突出订单、库存、支付和消息；考试平台突出权限、幂等、SQL 优化和部署。两个项目都在写“负责接口开发”，读者看不出区别。

每个项目至少保留一条完整链路。比如：

```text
下单 -> 扣库存 -> 发送支付结果 -> 更新订单 -> 超时关单 -> 恢复库存
```

面试官可以顺着这条链路问事务边界、消息重复、超卖、回调和状态机。你能把这些回答完整，项目才有含金量。

## 项目条目怎么写到可追问

### 用“动作 + 技术 + 场景 + 结果”组织

一条项目职责可以拆成四个部分：

```text
动作：设计、实现、排查、优化、补充
技术：条件更新、Lua、RabbitMQ、索引、Sentinel
场景：并发下单、重复支付、热点缓存、慢查询
结果：动作生效、失败可恢复、查询变快、状态可核对
```

示例：

```text
针对重复支付回调，使用业务幂等键和订单状态条件更新实现消费幂等，
避免重复通知覆盖订单状态，并通过重复调用测试验证最终状态。
```

这里没有虚构 QPS，也没有写“保证系统稳定性”这种空话。“重复调用测试”和“最终状态”给出了验证方向，面试官可以继续问幂等键和状态条件。

### 量化数据必须有来源

响应时间、吞吐量、成功率、用户数和并发数只要写出来，就要能回答测试环境、数据量、工具、次数和统计口径。没有条件就不要量化，可以改成：

- 输出数据库影响行数。
- 记录消息重试次数。
- 对比缓存命中前后的查询次数。
- 保存并发测试的成功和失败数量。
- 说明某个异常从发生到恢复的处理步骤。

结果不一定是百分比。能证明问题被定位、复现和修复，本身就有价值。

### 课程项目要写清边界

公开课程项目可以写简历，但要满足两个条件：

1. 你确实运行、修改或排查过其中的代码。
2. 你能区分课程提供的功能和自己补充的实现。

项目名可以换成业务名称，身份可以写成“个人实践项目”，但不要写“负责整体架构设计”“主导线上部署”或编造团队人数。面试官问来源时，直接说基于公开课程资料复现即可。

## 投递前检查

1. 求职意向是否和投递岗位一致，技能关键词是否覆盖 JD 中的核心要求。
2. 学校、联系方式、项目日期和技术版本是否有拼写或数字错误。
3. 每条项目经历是否包含动作、技术、场景和结果，是否至少有一条完整业务链路。
4. 是否删除了没有证据的 QPS、用户量、线上事故、集群和团队规模。
5. 是否能解释每个技术名词对应的代码、表、Key、消息或命令。
6. 是否保留了一页以内的长度，项目顺序是否按相关性排列。
7. PDF 文件名是否清晰，例如 `姓名-Java后端开发-学校.pdf`。
8. 投递不同 JD 时，是否调整了技能顺序和项目重点，而不是一份简历投所有岗位。
