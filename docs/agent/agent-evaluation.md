## 只看最终答案，你会漏掉 Agent 一半的问题

做 Agent 的人最容易犯的一个错误是：用"最终答案对不对"来判断 Agent 好不好。

答案对了就完事大吉，答案错了就调 Prompt、换模型、加工具。这个思路在普通的 Chatbot 场景里还行得通，但放到 Agent 场景里，问题很大。

Agent 和普通 Chatbot 的区别是什么？Agent 会自己做规划、调用工具、根据结果调整下一步。它不是"一问一答"，而是"思考-行动-观察-再思考"的循环。这个循环过程中，可能出现各种问题：

- 答案是对的，但调用了 15 次工具，其中 10 次完全没必要
- 答案是对的，但跳过了关键的权限校验步骤
- 答案是对的，但纯属巧合——工具调用错了，模型瞎猫碰上死耗子
- 答案错了，但规划逻辑是对的，只是某个工具返回了异常数据
- 答案错了，但 Agent 及时发现并尝试了补救，只是最终没成功

如果只看最终答案，这些差异全部被抹平了。你不知道 Agent 是"蒙对的"还是"真的会做"，也不知道优化应该从哪下手。结果评测的分数上去了，生产环境可能还是一团糟。

这篇文章系统梳理 Agent 评测的完整框架：结果、过程、成本三个层次，以及每个层次的具体指标和实现方法。读完以后，你应该能给自己的 Agent 搭一个最基本的评测体系。

## 评测的三个层次：结果、过程、成本

Agent 评测可以分成三个层次，每层关注的问题不同：

```text
┌─────────────────────────────────────┐
│  结果层：任务完成了吗？答案对不对？    │  ← 最直观，但信息量最少
├─────────────────────────────────────┤
│  过程层：怎么走过来的？路走对了吗？    │  ← 定位问题的关键
├─────────────────────────────────────┤
│  成本层：花了多少时间、token、钱？     │  ← 决定能不能规模化
└─────────────────────────────────────┘
```

| 层次 | 核心问题 | 典型指标 | 定位能力 |
| --- | --- | --- | --- |
| 结果层 | 任务成功了吗？ | 任务成功率、答案正确率 | 差——只知道好坏，不知道为什么 |
| 过程层 | 每一步对不对？ | 工具选择准确率、参数正确率、步骤合理性 | 强——能定位到具体哪一步出了问题 |
| 成本层 | 代价有多大？ | 平均步数、token 消耗、耗时、费用 | 中——知道效率高不高 |

三层不是互斥的，而是互补的。一个健康的评测体系应该同时覆盖这三层。下面分别展开。

## 第一层：结果评测（Outcome Evaluation）—— 任务到底完成了没有

结果评测是最基础的，回答"任务成功了吗"这个问题。虽然信息少，但它是最终的北极星指标——用户不关心你过程多优雅，只关心事情办成了没有。

### 任务成功率怎么算

任务成功率（Task Success Rate）看起来简单：成功的任务数 ÷ 总任务数。但"成功"怎么定义，里面大有文章。

**1. 二元判定（成功/失败）**

最简单的方式：任务要么成功，要么失败。

```text
成功率 = 成功任务数 / 总任务数
```

适合目标非常明确的任务，比如"查询订单号 12345 的物流状态"，答案唯一，对错分明。

**2. 部分得分（Partial Credit）**

很多任务不是非黑即白的。比如"帮我订一张明天去北京的机票"，Agent 找到了航班但没完成支付，算成功还是失败？

这时候需要部分得分。常见的做法是把任务拆成几个子目标，每个子目标占一定分数：

```text
任务：订一张明天去北京的机票
子目标：
  - 正确理解出发地和目的地  [10分]
  - 查到正确日期的航班       [20分]
  - 筛选出符合价格范围的      [20分]
  - 正确填写乘客信息         [20分]
  - 完成支付流程            [30分]
```

Agent 完成了前三个子目标，就得 50 分。部分得分的好处是能区分"差一点成功"和"完全跑偏"，对优化更有指导意义。

**3. 最终状态验证（Final State Verification）**

有些任务的结果不是一段文字，而是环境状态的变化。比如"把文件 A 移动到文件夹 B"，成功与否要看文件是不是真的移过去了。

这时候需要一个独立的验证器，去检查环境的最终状态是否符合预期，而不是看 Agent 说自己成功了。

```text
预期最终状态：
  - folderB/ 下存在 fileA
  - 原位置不再有 fileA
  - 文件内容未损坏
```

最终状态验证比看 Agent 的输出可靠得多。Agent 可能会撒谎说自己完成了，但环境状态不会骗人。

### 结果评测的局限

结果评测的最大问题是：**它告诉你坏了，但不告诉你哪坏了**。

成功率从 60% 降到 50%，你知道出问题了，但不知道是工具调用错了、Prompt 改坏了、还是模型版本退化了。要定位问题，就得看过程。

## 第二层：轨迹评测（Trajectory Evaluation）—— 路走对了吗

轨迹评测看的不是终点，而是 Agent 走的每一步。它把 Agent 的完整执行轨迹（trajectory）拿出来，逐步骤检查。

一条典型的 Agent 轨迹长这样：

```text
Step 1: 思考 —— "用户想查订单物流，我需要先调用订单查询工具获取订单信息"
Step 1: 行动 —— 调用 order_query(order_id="12345")
Step 1: 观察 —— 订单存在，物流公司是顺丰，运单号 SF123456789

Step 2: 思考 —— "有了运单号，现在调用物流查询工具获取状态"
Step 2: 行动 —— 调用 logistics_query(tracking_no="SF123456789")
Step 2: 观察 —— 包裹已签收，签收时间 2026-10-10 14:30

Step 3: 思考 —— "信息完整了，可以回答用户了"
Step 3: 回答 —— "您的订单 12345 已于昨日下午签收..."
```

轨迹评测就是对这样的一步步做诊断。具体可以拆成六个维度：

### 维度一：工具选择准确率

Agent 选对工具了吗？该调用 `order_query` 的时候，它是不是调用了 `user_query`？

```text
工具选择准确率 = 选对工具的步骤数 / 有工具调用的总步骤数
```

这个指标低，通常说明 Prompt 里的工具描述不清楚，或者模型本身的工具调用能力弱。

常见的错误模式：
- 应该用工具 A，用了工具 B
- 可以直接回答的问题，非要调用工具
- 有更合适的工具不用，绕远路用别的工具

### 维度二：参数正确率

工具选对了，参数填对了吗？参数名对不对？参数值对不对？必填参数有没有漏？

```text
参数正确率 = 参数正确的工具调用数 / 总工具调用数
```

注意这里有个坑：参数"语法正确"和"语义正确"是两回事。`order_id="12345"` 语法上没问题，但如果用户问的是订单 67890，那语义上就是错的。

参数错误通常是最难排查的。模型可能理解了用户意图，但在提取参数时出了偏差，或者参数格式和工具要求不一致。

### 维度三：步骤顺序合理性

多步骤任务中，Agent 的步骤顺序对吗？有没有依赖关系搞反了？

比如订机票的正确顺序是：查航班 → 选航班 → 填乘客信息 → 支付。如果 Agent 先填乘客信息再查航班，顺序就反了。

TRAJECT-Bench（ICLR 2026）专门针对这个问题设计了评测集，区分"串行依赖"和"并行独立"的工具调用，检查 Agent 是否理解步骤之间的依赖关系。[$TRAE_REF](https://en.papernotes.org/ICLR2026/llm_agent/traject-bencha_trajectory-aware_benchmark_for_evaluating_agentic_tool_use/)

顺序错了，有时候结果碰巧还是对的，但这属于"蒙对的"，换个场景可能就翻车了。轨迹评测能把这种情况揪出来。

### 维度四：工具幻觉

Agent 有没有调用根本不存在的工具？有没有编造工具的返回结果？

工具幻觉（Tool Hallucination）是 Agent 常见的问题之一。模型可能"觉得"某个工具应该存在，就直接调用了；或者工具返回了异常，模型假装看到了正常结果。

```text
工具幻觉率 = 幻觉调用次数 / 总工具调用次数
```

严重的工具幻觉会导致 Agent 在错误的道路上越走越远，而且它自己还意识不到。

### 维度五：自我修正能力

Agent 发现自己错了以后，能不能修正？调用工具失败了，是重试、换个工具，还是直接放弃？

自我修正能力是 Agent 智能程度的重要体现。一个只会"一次尝试，不行就拉倒"的 Agent，和一个能分析失败原因、调整策略再试的 Agent，价值差很多。

衡量方式：
- 失败后成功修正的比例
- 平均需要几次修正才能成功
- 修正方向是否合理（不是瞎试）

### 维度六：多余步骤和效率

有没有多余的工具调用？能不能三步完成的，走了八步？

多余步骤不一定是坏事——有时候多确认一下更稳妥。但如果大部分多余调用都是无效的，说明 Agent 的规划能力有问题，或者 Prompt 引导得不好。

多余步骤还直接影响成本和延迟。每多一次工具调用，就要多花一轮模型推理的时间和钱。

## 第三层：效率与成本评测 —— 花了多少代价

结果对了，过程也对了，然后呢？然后要看代价。

一个用 50 步、花费 5 美元完成任务的 Agent，和一个用 3 步、花费 5 美分完成同样任务的 Agent，商业价值天差地别。

### 时间成本

- **端到端延迟**：从用户发请求到拿到最终答案，总共花了多长时间
- **平均每步耗时**：每一轮思考-行动-观察花多久
- **工具调用耗时**：每个工具本身的执行时间

延迟直接影响用户体验。超过 10 秒用户就会觉得慢，超过 30 秒可能就走了。

### Token 成本

- **总 token 消耗**：输入 + 输出一共多少 token
- **输入输出比**：输入 token 是输出的多少倍（Agent 通常输入远大于输出）
- **每步 token 增量**：每多一轮对话，历史记录多了多少 token

Token 成本和模型定价直接挂钩。GPT-4o 级别的模型，一次复杂任务可能要消耗几十万美元的 token，规模化的时候这是一笔大钱。

### 工具调用成本

- **平均工具调用次数**：完成一个任务平均调用几次工具
- **工具调用成功率**：工具调用本身的成功率（网络超时、接口错误等）
- **第三方 API 费用**：有些工具调用本身就要花钱（比如搜索 API、数据库查询）

### 一个实用的成本指标：单次任务成本

把上面几项合起来，可以算出单次任务的平均成本：

```text
单次任务成本 = 模型 token 费用 + 工具调用费用 + 计算资源费用
```

这个指标直接决定了 Agent 的商业模式能不能成立。如果完成一个任务要花 2 美元，而用户只愿意付 0.5 美元，那就是亏本买卖。

## LLM-as-Judge：好用，但不是万能的

评测 Agent 的时候，很多地方需要"判断"——答案对不对、步骤合不合理、工具有没有选错。这些判断不是简单的字符串匹配能搞定的。

于是出现了 LLM-as-Judge 的做法：用另一个大模型当裁判，给 Agent 的表现打分。

### LLM-as-Judge 的优点

- **灵活**：能判断语义等价、逻辑合理性、内容质量等模糊的东西
- **快速**：不用人工标注，自动就能跑
- **可扩展**：有多少任务就能评多少任务

### LLM-as-Judge 的问题

**1. 裁判自己也会错**

大模型当裁判也会犯错误。它可能被长度误导（越长的回答分数越高），可能被语气影响（自信的回答得分更高），也可能有自己的偏好。

有研究表明，LLM-as-Judge 和人类判断的一致性大约在 70%-90% 之间，具体取决于任务类型和模型大小。 [$TRAE_REF](https://aiwiki.ai/wiki/agent_evaluation)

**2. 位置偏见**

如果让裁判比较两个答案哪个好，它可能倾向于选第一个（位置偏见）。解决方法是多次比较、交换顺序、取平均。

**3. 无法验证事实**

裁判模型也不知道事实真相。如果 Agent 给出了一个看起来很合理但完全错误的答案，裁判可能也发现不了。

所以 LLM-as-Judge 适合评估"表达好不好、逻辑通不通"，不适合评估"事实对不对"。事实正确性最好用确定性的验证器。

### 正确的使用姿势

- 能用代码自动验证的，不用 LLM 裁判
- 用 LLM 裁判时，给它明确的评分标准和参考依据
- 关键指标用多个裁判投票，减少随机误差
- 定期抽样人工复核，校准裁判的准确性

## 怎么搭一个实用的 Agent 评测框架

讲了这么多维度，落地的时候从哪开始？这里给一个分阶段的路线图。

### 第一阶段：先有结果评测

最开始不用搞复杂。先做三件事：

1. **准备评测集**：选 20-50 个典型任务，每个任务有明确的预期结果。任务要覆盖常见场景和边界情况。
2. **跑通自动化评测**：写个脚本，批量运行 Agent，记录每个任务的输出。
3. **计算任务成功率**：用代码或 LLM-as-Judge 判断每个任务是否成功，算出总体成功率。

这个阶段的目标是有一个基线。你不知道自己做得好不好，但至少以后改了什么，能知道是变好了还是变差了。

### 第二阶段：加上过程评测

结果评测稳定以后，开始看过程：

1. **记录完整轨迹**：把每一步的思考、工具调用、观察结果都存下来，结构化保存。
2. **计算过程指标**：工具选择准确率、参数正确率、平均步数、幻觉率。
3. **错误分类**：把失败的任务按原因分类——是工具选错了、参数填错了、还是规划错了。

错误分类很重要。它告诉你优化的优先级：如果 80% 的失败都是参数错误，那你就应该先去优化参数提取的 Prompt，而不是去换模型。

### 第三阶段：加入成本和效率

当 Agent 效果差不多了，开始关注效率：

1. **统计成本指标**：每个任务的 token 消耗、耗时、费用。
2. **建立效率基线**：知道当前的平均成本是多少。
3. **做性价比分析**：换个便宜点的模型，效果降多少？值不值？

这个阶段的目标是找到效果和成本的平衡点。不是效果越好越好，而是在可接受的成本下，效果尽可能好。

### 第四阶段：持续监控

上线以后，评测不能停：

1. **线上抽样评测**：定期从真实流量中抽样评测，监控效果是否退化。
2. **Bad Case 收集**：把用户反馈不好的案例收集起来，加入评测集。
3. **版本对比**：每次更新 Prompt 或模型，都和上一版跑对比评测，确认没有回退。

## 常见的评测陷阱

做 Agent 评测，有几个坑特别容易踩：

### 陷阱一：评测集和训练集重合

如果你用 Prompt 优化时反复测试的那些例子来做评测，分数肯定高，但不代表真实效果。评测集必须和开发用的例子分开，而且要定期更新，防止过拟合。

### 陷阱二：只看平均分

平均分从 75 升到 80，看起来不错。但可能是简单任务从 90 升到 95，把平均分拉上去了，难的任务反而从 50 降到了 40。

一定要分难度、分场景看指标。不同类型的任务分开统计，才能看到真实的变化。

### 陷阱三：用人类水平做参照

很多人喜欢说"我们的 Agent 达到了人类水平的 80%"。这个说法通常没什么意义。人类和 Agent 的错误模式完全不一样——人类容易犯粗心的错，Agent 容易犯离谱的错。两者的正确率数字可能接近，但用户体验完全不同。

更有意义的做法是和自己的上一版比，和明确的业务目标比。

### 陷阱四：评测本身的成本被忽略

跑一整套评测可能要花几百上千美元的模型费用。如果每次改个 Prompt 都跑全量评测，成本会很高。

实用的做法是：日常开发用一个小的"冒烟评测集"（10-20 个任务），快速验证基本功能没坏；版本发布前再跑全量评测集。

## 小结

Agent 评测不是一个单一的数字，而是一个多维度的评估体系。只看最终答案，你会错过过程中的大量问题。

一个完整的评测框架至少要覆盖三层：

- **结果层**：任务成功率、答案正确率。它告诉你"好不好"。
- **过程层**：工具选择准确率、参数正确率、步骤合理性、幻觉率、自我修正能力。它告诉你"为什么好/不好"。
- **成本层**：token 消耗、耗时、费用、平均步数。它告诉你"性价比怎么样"。

落地的时候不用一次性搞全。从结果评测开始，先建立基线；然后逐步加入过程指标，定位问题；再关注成本效率，找到平衡点；最后建立线上监控，持续迭代。

评测的终极目的不是打分，而是驱动改进。每一个指标都应该对应一个可操作的优化方向。如果一个指标你不知道怎么提升，那它暂时就不值得花精力去测。
