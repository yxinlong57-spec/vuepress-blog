前一篇[《用 Java 手写一个最小 RAG》](./java-minimal-rag.html)把 RAG 的五个环节跑通了，但它覆盖的只是最朴素的形态：一次向量召回、取 Top-K、直接拼 Prompt。这种实现有三宗罪——**召回不全**（相关信息压根没进候选集）、**排序不准**（进了候选集但排在后面被截掉）、**答不对也不会说不会**（库里没有答案照样编一个）。前两宗是检索质量问题，第三宗是流程问题：朴素 RAG 里没有任何一步负责判断"证据够不够"。核心结论很直接：这三宗罪靠换更好的嵌入模型只能缓解一小部分，真正的解法是在检索外面加一层控制——查询改写做多路召回、关键词与向量混合、对候选重排、对证据做充分性判断并在不足时再来一轮。

这一层控制就是 **Agentic RAG**（自适应检索）与朴素 RAG 的本质差别：检索从「一次性动作」变成「可循环、可判断、可放弃」的过程。下面用纯 Java 把这条流水线手写出来并真实跑一遍：同一批 5 个问题，分别走①朴素单次检索、②混合召回、③混合召回+多查询改写+RRF 融合、④再加一轮自我纠错循环，看每一层分别修好了哪类问题。

## 一、朴素 RAG 的边界在哪

先给上一篇文章的结论收个尾：**朴素 RAG 的边界，就是"检索一次"这四个字**。

我把它拆成四个具体的边界，每一条都会在后面的实测里出现。

**边界一：单次召回，一次定生死。** 用户的问题只被当成一次查询用掉。问题措辞和文档措辞对不上（用户说"用词对不上怎么办"，文档写"词汇鸿沟"），这一枪打空就没有第二次机会。实测里的 Q3 就是这种情况：目标片段 D9 在朴素方案的 Top-2 里完全没有出现——不是"差一点"被截掉，而是压根没进候选。

**边界二：单一检索通道。** 只用向量。向量擅长语义相似，但对精确术语、代号、数字这类"低频但决定性"的词元不敏感。反过来，关键词检索（BM25）擅长精确匹配但对同义改写无能为力。只用一个通道，就等于把另一类问题的命中率直接放弃。

**边界三：无条件相信检索结果。** Top-K 检索有个天然缺陷：不管你问什么，它总能返回 K 条。库里没有答案时，它返回的是 K 条噪声，而朴素 RAG 会把噪声当证据塞进 Prompt。实测里的 Q5（问公司年假折算标准，语料库里根本没有这类片段）在方案①下依然"答"出来了——因为从流程上看，没有任何一步会去质疑检索结果。

**边界四：没有充分性判断，也就没有"说不会"的出口。** 上一篇文章在 Prompt 里写了"资料里没有就说不知道"，这是把判断权交给模型自觉。实测结果很直接：Q5 方案①下，Mock LLM 依据两条完全不相干的片段，给出了"未休年假按日工资的 200% 折算"这样一个听起来很合理的错误答案。约束写在 Prompt 里不等于流程里有闸门。

把这四条合起来看，朴素 RAG 的问题不是"某个参数没调好"，而是**流程里缺少决策环节**：没有决定"换个问法再查一次"的环节，没有决定"多通道一起查"的环节，没有决定"证据够不够、要不要放弃"的环节。补上这些环节，就是 Agentic RAG。

## 二、Agentic RAG 的四个改造点

Agentic RAG 这个词最近很热，但落地时它并不神秘。相对于朴素 RAG，能加的控制点主要是四个，按"改造成本从低到高"排列：

| 改造点 | 解决哪条边界 | 具体做法 | 引入的额外开销 |
| --- | --- | --- | --- |
| 查询改写（多查询扩展） | 边界一：单次召回 | 用一次 LLM 调用把原问题扩展成 2~4 个检索友好的子查询，各自召回后融合 | 1 次 LLM 调用 + N 轮检索 |
| 混合召回 | 边界二：单一通道 | 关键词通道（BM25）+ 向量通道并行召回，用 RRF 融合排名 | 1 条额外检索通道 |
| 重排 | 边界二/三：排序不准 | 对融合后的候选做精排（交叉编码器或规则打分），只把最终 Top-K 送进 Prompt | 1 次重排计算（通常比召回贵） |
| 充分性判断 + 纠错循环 | 边界三/四：不会说不会 | 打分后判断证据是否足够；不足则基于反馈改写查询再来一轮，设轮次上限；仍不足就拒答 | 1 次判断 + 可能多一轮检索和改写 |

四个改造点里，前三个是"提高命中率"，第四个是"控制失败出口"。这两件事必须一起做：只提高命中率而没有出口，系统在真正没答案时照样会编；只有出口而没有召回手段，系统会过于频繁地拒答。

这里有个容易被忽略的定位问题：**Agentic RAG 里的 "Agentic" 指的是检索流程本身具备决策能力，而不是把检索包装成一个工具丢给 Agent 去调用**。两者经常被混为一谈，区别在于决策发生在哪一层：

- 前者（本文的做法）：改写、融合、判断、再来一轮的逻辑写在检索流水线内部，每一步都有明确的条件和上限，行为可预测、可测试。
- 后者：把 `search(query)` 当成工具交给 Agent，由模型决定调几次、怎么改词。行为上限依赖模型的自觉，容易出现无限查询或改写跑偏。

生产系统里两种都会用，但把控制逻辑放在流水线内部，是我更推荐作为基线的做法——因为它可以先跑通、可复现，再把"改什么词"这种需要创造力的部分交给模型。

## 三、纯 Java 手写这条流水线

实验设置：15 条中文技术片段构成的小语料（线程池、索引、RAG 各环节），5 个问题，其中 4 个的答案在语料里（金标片段分别是 D1、D6、D9、D10），第 5 个的答案故意不在语料里（用来检验"拒答"能不能被触发）。

**必须交代的两处模拟，以及为什么这么选：**

1. **LLM 全部用 Mock。** 真实模型每次输出都不一样，文章里的输出读者无法复现。所以改写脚本（多查询扩展、反馈式改写）和最终回答文本都写死在代码里，但**调用位置和调用次数是真实的**——成本统计直接反映真实流水线需要几次 LLM 调用。
2. **向量通道用"固定概念向量"模拟。** 真实的嵌入模型不能离线复现，所以我给每个片段和查询手工映射到一个 11 维概念空间（线程池、索引、RAG 流程、排名融合、混合检索、重排、查询改写、充分性纠错、BM25、幻觉拒答、工程实践），打分用内积。**这不是真实嵌入模型的行为**，它只用来稳定复现"语义通道会把泛话题排在精确术语前面"这个现象——也就是边界二。BM25 通道没有模拟，是完整实现的。

分词和打分是整个流水线的地基，先看这两块。

### 3.1 分词：中文没有空格，就用汉字 bigram

中文检索的第一个难题是分词。`ik`、`jieba` 这类分词器能做到更准的切分，但要引入第三方依赖。为了保持"单文件、无依赖"，这里用最朴素也最稳的做法：**汉字按连续片段切成 bigram（相邻两字），ASCII 字母数字按词切**。

```java
static boolean isCjk(char c) { return c >= 0x4E00 && c <= 0x9FFF; }
static boolean isWordChar(char c) { return (c >= 'a' && c <= 'z') || (c >= '0' && c <= '9'); }

static List<String> tokenize(String text) {
    String s = text.toLowerCase();
    List<String> tokens = new ArrayList<>();
    StringBuilder word = new StringBuilder();
    StringBuilder cjk = new StringBuilder();
    for (int i = 0; i < s.length(); i++) {
        char c = s.charAt(i);
        if (isWordChar(c)) {
            if (cjk.length() > 0) { addBigrams(cjk, tokens); cjk.setLength(0); }
            word.append(c);
        } else if (isCjk(c)) {
            if (word.length() > 0) { tokens.add(word.toString()); word.setLength(0); }
            cjk.append(c);
        } else {
            if (word.length() > 0) { tokens.add(word.toString()); word.setLength(0); }
            if (cjk.length() > 0) { addBigrams(cjk, tokens); cjk.setLength(0); }
        }
    }
    if (word.length() > 0) tokens.add(word.toString());
    if (cjk.length() > 0) addBigrams(cjk, tokens);
    return tokens;
}

static void addBigrams(StringBuilder sb, List<String> out) {
    if (sb.length() == 1) { out.add(sb.toString()); return; }
    for (int i = 0; i < sb.length() - 1; i++) out.add(sb.substring(i, i + 2));
}
```

bigram 的好处是**不需要词典**：任何中文串都能切成词元，`RRF 公式里的 k` 这种中英混排也不会散架（`rrf`、`公式`、`式里`、`里的`、`k`）。代价是词元数变多、粒度偏细，但对一个教学实现来说完全够用——后面 BM25 的 IDF 会自动压低"里的""什么"这类高频搭配的权重。

### 3.2 两条通道：BM25 与向量

关键词通道用 BM25，这是关键词检索的经典基线：词频饱和（TF 不会无限加分）、逆文档频率（IDF 惩罚高频词）、文档长度归一化。代码里的 `k1 = 1.2`、`b = 0.75` 不是我编的——它们正是 Lucene `BM25Similarity` 的默认值（已核对官方 javadoc，见参考资料）。查询时对语料做一遍打分排序：

```java
double score(int i, Map<String, Integer> qf) {
    double k1 = 1.2, b = 0.75;
    Map<String, Integer> d = tf.get(i);
    double dl = 0;
    for (int c : d.values()) dl += c;
    double s = 0;
    for (Map.Entry<String, Integer> e : qf.entrySet()) {
        Integer f = d.get(e.getKey());
        if (f == null) continue;
        s += idf(e.getKey()) * (f * (k1 + 1)) / (f + k1 * (1 - b + b * dl / avgdl));
    }
    return s;
}
```

向量通道就是一句内积（查询向量已归一化，片段向量保持原始权重，让"权重更高"的片段天然更靠前）：

```java
static double dot(double[] a, double[] b) {
    double d = 0;
    for (int i = 0; i < a.length; i++) d += a[i] * b[i];
    return d;
}
```

两条通道各取 Top-5 作为候选池。注意这里刻意没有"阈值过滤"——阈值属于后面的重排与充分性判断环节，候选池先尽量宽。

### 3.3 融合与重排：RRF 解决量纲，规则解决分布

两条通道的分数没法直接相加：BM25 是累加的 IDF 权重（可以到几十），向量内积是零点几这个量级的相似度。硬加权调参很脆弱，所以用 **RRF（Reciprocal Rank Fusion，倒数排名融合）**：完全丢掉原始分数，只看排名。

```java
static List<Hit> rrf(List<List<Hit>> lists, int k, int topN) {
    Map<Integer, Double> fused = new LinkedHashMap<>();
    for (List<Hit> l : lists)
        for (int r = 0; r < l.size(); r++)
            fused.merge(l.get(r).idx, 1.0 / (k + r + 1), Double::sum);
    List<Hit> out = new ArrayList<>();
    for (Map.Entry<Integer, Double> e : fused.entrySet()) out.add(new Hit(e.getKey(), e.getValue()));
    out.sort((x, y) -> Double.compare(y.score, x.score));
    return out.size() > topN ? new ArrayList<>(out.subList(0, topN)) : out;
}
```

`k` 是平滑常数：`k` 越大，排名靠前的差距被压得越平；`k` 越小，每个列表的第一名越占绝对优势。论文给的经验值是 60，代码里也取 60——工程侧有印证：Elasticsearch 的 RRF 实现把 `rank_constant` 默认设为 60（已核对官方文档，见参考资料）。本文未复现原论文的效果数据。

融合之后做一轮**规则重排**，打分公式是「查询词命中覆盖率 × 0.6 + 位置分 × 0.4」。位置分用 `1/(1+排名)` 表达"被前面环节排在前面本身就说明有相关性"这个先验：

```java
static List<Hit> rerank(List<Hit> candidates, List<String> queryTokens, BM25 index, int topN) {
    rerankCalls++;
    LinkedHashSet<String> q = new LinkedHashSet<>(queryTokens);
    List<Hit> out = new ArrayList<>();
    for (int r = 0; r < candidates.size(); r++) {
        Hit h = candidates.get(r);
        Set<String> docTokens = index.tf.get(h.idx).keySet();
        int matched = 0;
        for (String t : q) if (docTokens.contains(t)) matched++;
        double coverage = q.isEmpty() ? 0 : (double) matched / q.size();
        double position = 1.0 / (1.0 + r);
        out.add(new Hit(h.idx, 0.6 * coverage + 0.4 * position));
    }
    out.sort((x, y) -> Double.compare(y.score, x.score));
    return out.size() > topN ? new ArrayList<>(out.subList(0, topN)) : out;
}
```

生产环境里这一层通常替换成交叉编码器（cross-encoder），但**结构是一样的**：候选池进、精排结果出。把重排写成规则而不是模型，最大的好处是这一步可解释、零成本，方便先验证"重排有没有用"再决定要不要上模型。

### 3.4 充分性判断与纠错循环

这一步是本文的重点。判断标准用「证据与查询的相关分 / 查询词元数」，除以词元数是为了让不同长度的问题可比：

```java
static double adequacy(List<Hit> evidence, List<String> queryTokens, BM25 index) {
    Map<String, Integer> qf = new HashMap<>();
    for (String t : queryTokens) qf.merge(t, 1, Integer::sum);
    double best = 0;
    for (Hit h : evidence) best = Math.max(best, index.score(h.idx, qf));
    int distinct = new HashSet<>(queryTokens).size();
    return distinct == 0 ? 0 : best / distinct;
}
```

阈值定为 0.60——**这个数是在本实验语料上标定出来的经验值，换语料必须重新标定**（第六节会专门讲这个坑）。纠错循环的骨架：

```java
static List<Hit> scheme4(Query q, List<Doc> docs, BM25 index) {
    llmCalls++;                                  // 第 1 次改写：多查询扩展
    List<List<Hit>> lists = new ArrayList<>();
    lists.add(hybridRound(q.text, q.vec, docs, index, FINAL_K));
    for (RQ rq : q.expand) lists.add(hybridRound(rq.text, rq.vec, docs, index, FINAL_K));
    List<Hit> evidence = rrf(lists, RRF_K, FINAL_K);
    List<String> queryTokens = unionTokens(q.text, q.expand);
    lastAdequacy = adequacy(evidence, queryTokens, index);

    int round = 1;
    while (lastAdequacy < ADEQUACY && round < MAX_ROUNDS) {   // 上限：最多 2 轮
        llmCalls++;                              // 第 2 次改写：基于反馈
        round++;
        List<List<Hit>> more = new ArrayList<>(lists);
        for (RQ rq : q.feedback) more.add(hybridRound(rq.text, rq.vec, docs, index, FINAL_K));
        queryTokens.addAll(unionTokens("", q.feedback));
        evidence = rrf(more, RRF_K, FINAL_K);
        lastAdequacy = adequacy(evidence, queryTokens, index);
    }
    llmCalls++;                                  // 生成回答
    return evidence;
}
```

两个细节值得注意：

- **第二轮改写不是重复第一轮。** 第一轮的多查询扩展是"照原问题扩展"，不知道检索会返回什么；第二轮是**基于反馈**的改写（已经看到检索结果都不相关，于是改问更贴近机制的问题）。实测里 Q4 正是靠这个差别被修好的。
- **新一轮的候选不丢弃旧结果，而是把两个列表一起再融合一次。** 否则纠错循环会变成"用新答案覆盖旧答案"，把上一轮已经命中的正确片段冲掉。

## 四、实测：5 个问题 × 4 种方案

代码放在 `D:\temp\agentic-rag\Main.java`，运行方式（Windows PowerShell 下中文容易乱码，所以重定向到文件再读；实测这样能正常显示）：

```bash
cd D:\temp\agentic-rag

```

5 个问题是按"难度递进"设计的，每个问题对应一种特定的失败类型：

| 问题 | 提问 | 金标片段 | 想验证的失败类型 |
| --- | --- | --- | --- |
| Q1 | 线程池核心线程满了之后，新任务会怎么处理？ | D1 | 词面重合高，朴素方案应该能命中（对照组） |
| Q2 | RRF 公式里的 k 一般取多少？ | D6 | 语义通道把泛话题排在精确术语前面，排序不准 |
| Q3 | 捞回来的内容和资料里写的话对不上时，怎么才能查到正确的那一段？ | D9 | 用户用词与文档用词完全不一致（词汇鸿沟） |
| Q4 | 捞回来的材料看着挺多，但模型还是答不上来，流程该怎么兜底？ | D10 | 首轮多查询扩展没打中，需要基于反馈的第二次改写 |
| Q5 | 公司年假折算成现金的标准是多少？ | 无 | 库里没有答案，检验能不能拒答 |

下面是运行输出的关键片段（均为真实输出）。

**Q1：对照组。** 朴素方案就命中，后面的复杂方案只是保持命中：

```text
=================== Q1：线程池核心线程满了之后，新任务会怎么处理？ ===================
方案① 朴素单次检索（向量 Top-2，无重排）
  检索结果：D1(0.989)  D2(0.939)
  判定：✔ 命中 D1  （检索轮次 0，重排 0 次，LLM 调用 1 次，耗时 1.16 ms）
```

这里也能看出 Q1 的问题：D2（拒绝策略）被一起捞了进来，属于同主题噪声——朴素方案给不了"该丢哪条"的判断。

**Q2：排序不准被混合召回修好。** 注意朴素方案的两条结果分别是"排序融合的工程实现"和"混合检索"，精确讲 RRF 的那条 D6 连前二都没进：

```text
=================== Q2：RRF 公式里的 k 一般取多少？ ===================
方案① 朴素单次检索（向量 Top-2，无重排）
  检索结果：D13(1.239)  D7(0.914)
  判定：✘ 未命中 D6，给出偏题回答  （检索轮次 0，重排 0 次，LLM 调用 1 次，耗时 0.10 ms）
方案② 混合召回（BM25+向量→RRF）+ 重排
  检索结果：D6(0.533)  D13(0.200)  D12(0.200)
  判定：✔ 命中 D6  （检索轮次 1，重排 1 次，LLM 调用 1 次，耗时 0.71 ms）
```

修好的机制非常清楚：问题里带着 `RRF`、`k` 这两个低频词元，BM25 把它们当作高 IDF 特征，D6 直接排到 BM25 的第一名，于是进了 RRF 候选池；重排的"命中覆盖率"再把它从候选池的第 1 名稳住（`0.6 × 覆盖率` 这一项把只有 2 个词元命中的 D6 与其他泛话题拉开）。**这就是"混合召回"的价值：不是提高相似度，而是给精确术语一条独立的、不经过语义压缩的通道。**

**Q3：词汇鸿沟需要多查询改写给修好。** 这条最典型——朴素和混合方案都打空，因为问题里的用词（"内容和资料写的话对不上"）与文档用词（"词汇鸿沟"）几乎不共享任何词元：

```text
=================== Q3：捞回来的内容和资料里写的话对不上时，怎么才能查到正确的那一段？ ===================
方案① 朴素单次检索（向量 Top-2，无重排）
  检索结果：D5(0.915)  D14(0.852)
  判定：✘ 未命中 D9，给出偏题回答  （检索轮次 0，重排 0 次，LLM 调用 1 次，耗时 0.02 ms）
方案② 混合召回（BM25+向量→RRF）+ 重排
  检索结果：D5(0.422)  D12(0.244)  D14(0.133)
  判定：✘ 未命中 D9，给出偏题回答  （检索轮次 1，重排 1 次，LLM 调用 1 次，耗时 0.45 ms）
方案③ 多查询改写 + 混合召回 + RRF
  检索结果：D9(0.049)  D14(0.048)  D10(0.032)
  充分性分（证据相关分 / 查询词元数）=0.627，阈值 0.6 → 证据足够，可以回答
  判定：✔ 命中 D9  （检索轮次 4，重排 4 次，LLM 调用 2 次，耗时 1.08 ms）
```

注意方案②的两条噪声 D5、D12 是怎么来的：D5 是 RAG 流程综述，D12 谈幻觉与拒答，它们和"检索查不到"这个话题在词面上有零星重合。**混合召回本身对词汇鸿沟无能为力**——因为两条通道都在用原问题的词元。真正的解法是改写：把"怎么才能查到正确的那一段"改写成"怎么用查询改写缓解词汇鸿沟"，文档用词被显式写进子查询，D9 立刻命中。

**Q4：首轮改写没打中，靠第二次"带反馈的改写"修复。** 这是全文最有价值的一段对比。Q4 的首轮多查询扩展是"凭原问题想象"的三条子查询（该重试还是放弃、材料不相关怎么办、兜底流程），全都打空；充分性分只有 0.268，触发拒答：

```text
方案③ 多查询改写 + 混合召回 + RRF
  检索结果：D5(0.065)  D15(0.064)  D12(0.032)
  充分性分（证据相关分 / 查询词元数）=0.268，阈值 0.6 → 证据不足，拒绝回答
  Mock LLM 输出：资料中没有找到与问题相关的内容，无法回答。
  判定：✘ 未命中 D10，并且触发拒答  （检索轮次 4，重排 4 次，LLM 调用 2 次，耗时 0.83 ms）
方案④ 再加一轮自我纠错循环
  检索结果：D5(0.065)  D15(0.064)  D10(0.049)
  充分性分（证据相关分 / 查询词元数）=0.664，阈值 0.6 → 证据足够，可以回答
  Mock LLM 输出：依据资料 D5(0.065)  D15(0.064)  D10(0.049) 回答：做充分性判断，证据相关分低于阈值就改写查询再检索一轮。
  判定：✔ 命中 D10  （检索轮次 6，重排 6 次，LLM 调用 3 次，耗时 0.83 ms）
```

方案④比方案③多做的只有一件事：在证据不足时，用**已经看到的检索结果**作为反馈重新改写一次（"充分性判断 证据相关分低于阈值就再次检索"），于是 D10 被捞回候选池。充分性分从 0.268 抬到 0.664，跨过阈值，系统从"拒答"变成"答对"。

这里还有个细节值得看：D10 在最终 Top-3 里排第 3，分数只有 0.049，比 D5（0.065）低。**如果只取 Top-2，这一轮的纠错依然会失败。** 送进 Prompt 的条数（`FINAL_K=3`）本身就是远端召回和上下文噪声之间的一次权衡——取 2 条时 D10 进不来，取 5 条时噪声会显著增多。这也是第四层改造里"候选池宽度"比"排序精度"更关键的原因。

**Q5：库外问题，只有纠错循环会拒答。** 前三种方案都把两条不相干的片段当证据，编出了"未休年假按日工资的 200% 折算"：

```text
=================== Q5：公司年假折算成现金的标准是多少？ ===================
方案① 朴素单次检索（向量 Top-2，无重排）
  检索结果：D15(0.746)  D14(0.519)
  Mock LLM 输出：依据资料 D15(0.746)  D14(0.519) 作答：按公司现行规定，未休年假按日工资的 200% 折算成现金。
  判定：✘ 未拒答（Mock LLM 编造答案）  （检索轮次 0，重排 0 次，LLM 调用 1 次，耗时 0.01 ms）
方案③ 多查询改写 + 混合召回 + RRF
  充分性分（证据相关分 / 查询词元数）=0.000，阈值 0.6 → 证据不足，拒绝回答
  判定：✔ 正确拒答  （检索轮次 4，重排 4 次，LLM 调用 2 次，耗时 0.84 ms）
方案④ 再加一轮自我纠错循环
  充分性分（证据相关分 / 查询词元数）=0.000，阈值 0.6 → 证据不足，拒绝回答
  判定：✔ 正确拒答  （检索轮次 5，重排 5 次，LLM 调用 3 次，耗时 0.69 ms）
```

Q5 的充分性分是 0.000——检索回来的每一条都和问题毫无关联，所以任何阈值都能拦住它。这也说明**拒答出口的有效性依赖打分机制**：如果这里用的还是固定 Top-K、没有证据相关分，那 Q5 永远拦不住。

**汇总。** 程序的最终汇总输出：

```text
=================== 汇总 ===================
①朴素单次检索  命中 1/5，正确拒答 0/1
②混合召回+重排  命中 2/5，正确拒答 0/1
③多查询RRF      命中 3/5，正确拒答 1/1
④再加纠错循环    命中 4/5，正确拒答 1/1
```

换成表格看"哪种问题在哪种方案下被修复"：

| 问题 | ①朴素 | ②混合召回+重排 | ③多查询+RRF | ④加纠错循环 | 首次被修复的方案 |
| --- | --- | --- | --- | --- | --- |
| Q1（词面重合） | ✔ | ✔ | ✔ | ✔ | ①（朴素本身够用） |
| Q2（精确术语被泛话题挤下） | ✘ | ✔ | ✔ | ✔ | ② 混合召回 |
| Q3（词汇鸿沟） | ✘ | ✘ | ✔ | ✔ | ③ 多查询改写 |
| Q4（首轮改写没中） | ✘ | ✘ | ✘ | ✔ | ④ 带反馈的纠错循环 |
| Q5（库外问题） | ✘编造 | ✘编造 | ✔拒答 | ✔拒答 | ③ 充分性判断 |

一个反常识但重要的结论：**这四层改造不是"叠加越多越好"，而是每层各自负责一类问题。** Q2 在方案③④下并没有变得更好（命中数不再增加），因为它的失败点（精确词元被语义通道稀释）已经在第二层被解决，多查询和纠错循环对它只是额外成本。判断"该不该加一层"的正确方式，是看你这批真实问题里，有多少条的失败原因落在这一层能覆盖的类型上。

## 五、成本与延迟：多一轮检索值不值

前面每种方案的输出里都带了"检索轮次 / 重排次数 / LLM 调用次数"的计数，最后一列是单次耗时。把单次耗时单独看没有意义（毫秒级抖动大），更有价值的是**每层改造的调用量倍数**。按 5 个问题累计：

| 方案 | 每问检索轮次 | 每问重排次数 | 每问 LLM 调用 | 相对消耗 |
| --- | --- | --- | --- | --- |
| ①朴素 | 0（单次向量扫描） | 0 | 1（生成） | 1× |
| ②混合召回+重排 | 1 | 1 | 1 | 检索 2×，多 1 次重排 |
| ③多查询+RRF | 3~4 | 3~4 | 2（改写+生成） | 检索 3~4×，多 1 次 LLM |
| ④加纠错循环 | 3~6 | 3~6 | 2~3 | 最坏情况再翻一倍 |

真正决定"值不值"的是**单轮检索的绝对延迟**，这与库的规模强相关。所以我另做了一组真实测量：把 15 条语料复制扩展到 20000 条片段建内存索引，对同一问题跑 20 次取平均：

```text
===== 成本实验：内存索引 20000 条片段 =====
建索引耗时：662.4 ms
BM25 扫描打分（20000 条，每轮）：32.3 ms
向量全量打分（20000 条 × 11 维，每轮）：6.3 ms
RRF 融合（6 候选，每轮）：0.07 ms
规则重排（6 候选，每轮）：0.07 ms
一轮混合召回合计：约 38.7 ms
```

（同一台机器多次运行，BM25 一项在 26~33 ms 之间波动；这组数字的绝对值只对这台机器成立，请不要直接搬到容量规划里。）

从这组数据能读出三件事：

1. **融合与重排本身几乎不要钱**（0.07 ms 量级），因为它们只处理几条到几十条候选。这就是为什么"召回 Top-N 再重排"是标准做法：贵的是召回，重排是捡便宜的。
2. **这里的 BM25 是"扫描式"实现**（对全库逐条打分），所以它是耗时大头——真实系统用倒排索引，查询成本只和 posting list 长度相关，通常远低于全库扫描。**所以 38.7 ms / 轮是上界，不是真实系统的值。** 向量通道同样：这里是 20000 条 × 11 维的全量扫描，真实系统用 HNSW、IVF 这类 ANN 索引，代价换精度，能快几十倍。
3. 按这个上界估算：一轮 38.7 ms，方案③ 每问 4 轮 ≈ 155 ms；方案④ 最坏 6 轮 ≈ 232 ms，再叠加两次改写 LLM 调用的实际延迟（真实场景通常几百毫秒到几秒，远大于本地检索）。**结论是：检索轮次本身不是延迟瓶颈，LLM 改写调用才是。**

那么什么时候不值得加这些层？我的判断标准是三条：

- **你的问题几乎都是"问什么词、文档里就有什么词"的形态**。这时第二层（混合召回）以外的改造收益都很小，反而会让延迟和成本翻几倍。
- **库很小（千条以内）且更新频繁**。小库上混合召回和重排的收益不稳定，而多查询改写和纠错循环的 LLM 成本是固定的，性价比差。
- **场景对延迟极敏感（比如在线打字的实时补全）**。这类场景里"多一轮 LLM 改写"直接不可接受；反过来，离线批处理、后台问答这类场景几乎没有延迟预算压力，把四层全开是合理的。

反过来说，**当拒答是硬需求时（企业知识库、合规问答、客服），第四层几乎不可省**——因为它不是"提高质量"，而是"失败时不出错"的兜底。前面 Q5 的实测已经说明了这一点。

## 六、四个容易踩的坑

**坑一：查询改写把意图改跑。** 多查询扩展最容易出的错是"改出了原问题没问的东西"。实测里 Q4 的第一轮扩展（"该重试还是放弃""材料不相关怎么办"）就是把"证据不足时的流程兜底"这个问题，改写成了"要不要重试"这个方法论问题，三条子查询全部打空——而这次改写也白白花掉了一次 LLM 调用和三轮检索。三条缓解措施：改写结果只作为**追加通道**，原问题必须始终参与召回（本文就是这么做的）；对改写结果做长度和关键词的粗筛，明显跑题的丢弃；把"改写不得引入新实体"写进改写 Prompt。

**坑二：RRF 的 k 值选不对。** `1/(k + rank)` 这个公式对 `k` 非常敏感。`k` 太小（比如 1），第一名几乎通吃，另一个通道的好结果被完全淹没，融合退化成"单通道"；`k` 太大（比如 1000），所有排名被压平，融合变成简单投票，精确匹配的优势没了。用 60 这类中间值是稳妥起点，但真正靠谱的做法是**在你自己的评测集上扫一遍 k**。这里还有个别扭点：多个列表融合时，同一个文档出现在 3 个列表里会累加 3 次分数，等于被"投票加权"——这通常是我们想要的，但如果你发现长尾噪声片段因为到处露脸而排到前面，就该降低列表数量或对贡献次数做上限。

**坑三：重排比召回还慢。** 本文的重排是规则打分（0.07 ms），但换成真实的交叉编码器就完全不同了：cross-encoder 要对「(查询, 文档)」这样的**成对**输入跑一遍模型，6 条候选就是 6 次前向推理，延迟可能到几十到几百毫秒，比召回本身贵一个量级。所以生产里必须控住两个量：候选条数（本文是 6，常见做法 20~50）和重排条数。如果发现整体延迟吃紧，第一件事是砍候选，不是砍重排。

**坑四：无限纠错循环。** 这是最危险的一个。纠错循环天生有"再试一次说不定就好了"的倾向，如果不设上限，最坏情况是：改写 → 检索 → 判断不足 → 再改写 → 再检索……每一轮都消耗一次 LLM 调用。必须同时设两个上限：**轮次上限**（本文 `MAX_ROUNDS = 2`）和**总预算上限**（token 或耗时）。另外，判断"不足"的阈值不能设得太高——阈值过高会让正常问题也反复触发循环，看起来在"认真检索"，实际只是烧钱。本文阈值 0.60 的由来也在这里：它是**在实测到的这几组分值之间取的分界点**（Q5 0.000、Q4 首轮 0.268、Q3 0.627、Q4 补足后 0.664、Q1 0.859、Q2 1.145），把"库里没答案"的两组（0.000、0.268）和"有答案"的四组（≥0.627）分开。换一批语料，这个数必须重新标定，直接抄过去一定会出现"该拒答的不拒答"或"该回答的反复拒答"。

## 七、面试官视角怎么答

这一类问题在面试里出现得越来越多（"你们 RAG 召回不准怎么优化""了解 Agentic RAG 吗"），可以按"先划边界，再给方案，最后给判断依据"三层来答：

**问：RAG 召回不准，你会怎么排查和优化？** 答：先分层定位，别一上来就换嵌入模型。召回不全（金标根本没进候选池）要动召回层——加关键词通道做混合召回、加查询改写作多路召回；进了候选池但排序靠后要动重排层——先召回 Top-20 再精排取 Top-3；如果连"错在哪一层"都不知道，就先建评测集，分别看 Recall@K 和最终答案正确率，两者一起差是召回问题，Recall 高但答案差是排序或生成问题。

**问：Agentic RAG 和普通 RAG 的区别是什么？** 答：普通 RAG 是"检索一次 → 生成"，Agentic RAG 是"检索 → 判断 → 需要就改写再检索 → 生成/拒答"。核心差别不在模型，而在流程里多了两个决策点：要不要再检索一次、证据够不够。我以为关键的是"Agentic"说的是**检索流程本身有决策能力**，而不是把检索包成工具丢给 Agent 让它自己决定——后者的行为上限受模型自觉约束，前者可以设阈值、设上限、写测试。

**问：怎么防止 RAG 幻觉？** 答：把"不知道"做成流程出口而不是 Prompt 里的一句叮嘱。具体就是本文第四层——对证据打相关分，低于阈值（并在有限轮次内无法补足）时返回"资料不足"，而不是把噪声塞进 Prompt 让模型圆场。实测里 Q5 在方案①②下会编出一条规定，方案③④才拒答，差别不在模型多聪明，而在流程里有没有这一步。

**问：这些层全加上，成本和延迟怎么办？** 答：先算账再加层。融合和重排基本不要钱（毫秒级），贵的是**多轮改写带来的 LLM 调用**和**候选条数带来的重排成本**。我的做法是先只加"混合召回+重排"这两层（收益最稳定、成本最低），等评测集显示还有一批问题是因为词汇鸿沟漏召回的，才加多查询改写，最后才加纠错循环兜底。

## 小结

这篇是[《用 Java 手写一个最小 RAG》](./java-minimal-rag.html)的进阶篇，把朴素 RAG 的四个边界逐一补上：

1. **单次召回** → 多查询改写（多路召回 + RRF 融合）。实测 Q3 靠这一层从"打空"到命中。
2. **单一通道** → 混合召回（BM25 关键词 + 向量）。实测 Q2 靠这一层把"只有精确词元才认得出"的那条片段捞回候选池，并稳到第 1 名。
3. **无条件相信 Top-K** → 充分性判断。实测 Q5 靠这一层从"编造规定"变成"正确拒答"。
4. **不会说不会** → 纠错循环 + 拒答出口（带轮次和预算上限）。实测 Q4 靠"基于反馈的第二次改写"修复，充分性分从 0.268 抬到 0.664。

真实数据给出的整体结果就是那句汇总：命中从 1/5 提升到 4/5，剩下那个（Q5）的正确答案本来就是拒答，也由第四层给出。更重要的是，这次实验把"每层各自负责哪类问题"量化出来了——**能拿到这种结论，靠的不是调参，而是把小语料、可复现 Mock、逐层对照放在了一起跑**。这也是我现在做 RAG 优化时的固定动作：先建能复现的评测，再加层；每加一层都必须能回答"它修好了哪几条原来修不好的问题"。

代码在 `D:\temp\agentic-rag\Main.java`，单文件 JDK 11 可直接运行；把 `tokenize` 换成真实分词器、`dot` 换成真实嵌入、重排换成 cross-encoder，骨架和实测的方法完全不用改。
