黑马点评简历怎么写？别只堆缓存三兄弟，给出一份能追问的 Redis 项目模板

Loong2026/10/3大约 11 分钟面经手册求职简历Redis

先说结论

黑马点评很适合用来证明 Redis 能力，但“实现缓存穿透、击穿、雪崩”已经成了高度同质的项目描述。面试官真正想知道的，是你能不能把 Redis 键、数据库记录、并发请求和失败恢复串起来。

更可信的写法是从登录、缓存、秒杀和消息四条链路中挑两条做深。比如“Lua 原子扣减优惠券库存 + 数据库唯一约束 + Redis Stream 异步下单”比单独列十个 Redis 数据结构更能说明问题。

下面是我写的一份草稿简历，供大家参考。项目按公开仓库的单机学习环境写，不补 QPS、生产集群、百万并发和没有实际跑过的中间件。

黑马点评 Redis 实战平台 | 个人实践项目
2026.06 - 2026.09

项目简介：基于 Spring Boot 和 Redis 构建本地生活点评与优惠券秒杀系统，
覆盖商户查询缓存、登录鉴权、优惠券秒杀、异步下单、点赞、关注、签到和附近商户
等场景，重点处理热点缓存、并发扣减、重复请求和消息可靠消费。

技术栈：Java 8、Spring Boot 2.7.4、MyBatis-Plus 3.5.2、MySQL、Redis、
Redisson 3.17.7、Lua、Redis Stream、Hutool 5.8.8

核心工作：

1. 基于 Redis Token 和双拦截器实现登录态校验与权限控制，设计 Token 过期刷新、
   登出失效和用户信息缓存，避免每次请求直接查询数据库；对拦截器执行顺序、
   刷新响应头和线程上下文传递进行联调。

2. 针对商户、店铺类型等热点数据实现 Cache Aside 缓存，结合随机过期、空值缓存、
   互斥重建和逻辑过期控制缓存穿透与热点 Key 失效；在缓存删除和数据库更新之间
   保留重试与最终一致性校验。

3. 使用 Lua 脚本完成优惠券库存判断、一人一单校验和预扣减，保证 Redis 中判断与
   扣减的原子性；结合数据库唯一索引和订单记录，处理脚本成功但后续下单失败的
   补偿问题。

4. 基于 Redis Stream 和消费组将秒杀下单从请求线程中异步化，记录消息 ID、
   订单状态和消费结果；处理消费失败、Pending 消息、重复消费和确认后宕机，
   通过业务唯一键避免重复创建订单。

5. 使用 Redisson 处理跨线程和跨实例的互斥场景，核对锁 Key、等待时间、租期和
   看门狗续期边界；对锁过期后业务仍未完成的情况补充状态校验和幂等保护。

项目验证：

- 在本地 Redis、MySQL 环境构造缓存未命中、热点 Key 重建和缓存与数据库不一致
  场景，记录查询次数、缓存命中情况和数据库最终状态。
- 使用多线程请求验证 Lua 扣减和数据库唯一约束，保存库存变化、重复用户请求、
  订单数量和异常日志。
- 创建 `stream.orders` 消费组，模拟消费失败和重复投递，核对消息 ID、
  Pending 列表、ACK 和订单幂等结果。

如果不打算继续改，这份草稿已经比“使用 Redis 实现缓存和分布式锁”完整很多。下面讲每条描述怎么防守，以及哪些常见写法容易在面试中被追问到。

这份简历为什么不能只写缓存三兄弟

“缓存穿透、缓存击穿、缓存雪崩”是知识点，不是项目成果。它们可以被写成三个实现动作，但不能证明你理解具体业务。

同样写缓存，下面两种表达差距很大：

使用 Redis 解决缓存穿透、击穿和雪崩。
对不存在的商户 ID 缓存空值并设置较短过期时间；
热点商户缓存采用互斥重建，避免缓存失效瞬间请求全部落到 MySQL；
缓存过期时间增加随机抖动，降低同一时间批量失效的风险；
对缓存与数据库不一致的记录保留删除重试和定时校验。

第二版可以看到键、策略、请求现象和失败处理。面试官能继续问“为什么空值也要设置过期时间”“互斥重建拿不到锁时返回什么”，项目才有展开空间。

Redis Token 怎么写才不是一句配置

登录链路可以把下面几件事讲清楚：

动作关键设计可追问证据
登录成功后生成 Token使用随机串或 UUID，把用户信息存入 RedisToken Key、过期时间、登录响应
每个请求校验 Token双拦截器读取 Token、刷新有效期、放入 ThreadLocal拦截器顺序、请求日志、用户上下文
登出或封禁删除 Token，后续请求立即失效Redis 删除记录、接口返回
避免用户信息反复查库把必要字段随 Token 缓存缓存命中日志、数据库查询次数

不要把 Redis Token 写成 JWT 的替代品。两者都可以做登录态，区别在状态存放位置、撤销成本、服务端查询次数和跨服务共享方式。项目里实际用的是什么，就写什么。

缓存一致性怎么回答

Cache Aside 的读写顺序只是起点。面试官通常会追问：删除缓存失败怎么办、数据库更新成功但缓存删失败怎么办、并发读写会不会把旧值写回。

回答时先给出边界：

  1. 商户基础信息允许短暂不一致，数据库是最终依据。
  2. 更新数据库后删除缓存，缓存下一次读取时再重建。
  3. 删除失败写入重试记录或通过消息重试，不能只留在业务请求里。
  4. 对一致性要求更高的数据，减少缓存参与，或者使用版本号和更新条件。

不要承诺“强一致”。Redis 和 MySQL 是两个存储系统，网络、事务提交和进程失败都可能让两边暂时不同。项目里能做的是缩小不一致窗口，并提供检查和修复路径。

逻辑过期和互斥重建怎么区分

互斥重建的目标是防止大量并发请求同时查库。拿到锁的线程负责查询并写缓存，其他线程等待、重试或返回旧值。逻辑过期则让缓存值本身携带过期时间，即使物理 Key 还没过期，发现逻辑过期后也可以异步重建。

两者都在处理热点 Key，但关注点不同。互斥重建会带来锁等待和线程占用；逻辑过期允许返回旧值，需要业务能接受短时间数据不新。简历里要写到具体结果，而不是只写名词。

秒杀链路要写到“订单状态”

一个可解释的秒杀链路可以写成：

用户请求
-> Lua 校验库存和一人一单
-> Redis 预扣库存
-> 生成订单号
-> 发送到 stream.orders
-> 消费端校验并写入数据库订单
-> 创建数据库唯一约束兜底
-> ACK 消息

这里最容易漏掉的是“预扣成功之后失败怎么办”。Lua 脚本已经扣了 Redis 库存，但后续消息发送、消费或数据库写入都可能失败。项目需要至少能回答下面几个问题：

  • 消息发送失败时，Redis 库存和用户下单资格是否回滚。
  • 消费端重复收到同一个订单消息时，如何避免创建两条订单。
  • 数据库写入成功但 ACK 前宕机时，Pending 消息如何重新消费。
  • Redis 库存和数据库库存不一致时，用什么定时任务或对账逻辑修复。

为什么用 Lua，不只用 Redisson 锁

Lua 的价值是把多个 Redis 判断合成一次原子执行，适合“库存大于零、用户未购买、扣减库存”这类短操作。Redisson 锁适合跨线程或跨实例保护一段更长的业务逻辑，但锁的等待、续期、释放和业务超时都会引入新问题。

如果只是把整段下单逻辑包在分布式锁里，锁持有时间长，扣库存、查数据库和发消息都会放大锁竞争。更合理的组合是 Redis 原子预扣减 + 消息异步削峰 + 数据库唯一约束和事务兜底。

Redis Stream 怎么讲可靠消费

公开仓库使用 stream.orders 消费组，可以结合下面的命令解释：

XGROUP CREATE stream.orders g1 $ MKSTREAM

消费流程要能说清：

读取消息
-> 解析订单参数
-> 校验业务幂等键
-> 写入 MySQL
-> 返回成功
-> XACK 确认

消费失败时不要把消息直接丢掉。是否重试、重试多少次、什么时候进入死信处理，要根据业务决定。订单消息比点赞消息重要，不能套用同一个重试策略。

Redisson 锁过期后业务还没完成怎么办

Redisson 看门狗可以在业务未结束时续期，但续期不是万能的。JVM 长时间停顿、Redis 连接断开或业务设置过短租期时，锁仍然可能失效。

所以锁只能作为并发控制的一部分，不能替代业务幂等。扣减和写入要带唯一键，数据库要有唯一约束。锁失去后，重复请求最多被挡在业务状态判断或数据库约束上。

面试官会怎么追问

缓存穿透、击穿、雪崩分别怎么处理

穿透针对不存在的数据，常见做法是空值缓存、布隆过滤器或参数校验。击穿针对单个热点 Key 失效，可以用互斥重建或逻辑过期。雪崩是大量 Key 同时失效或 Redis 故障，可以通过过期时间抖动、多级缓存和故障降级缓解。

还要补一句边界：布隆过滤器有误判，空值缓存占内存，逻辑过期可能返回旧数据。方案要和一致性要求匹配。

秒杀怎么防止超卖

第一层是 Redis Lua 原子扣减，第二层是数据库唯一索引和订单状态，第三层是失败补偿和对账。不要把任何一层说成绝对可靠。只有把请求、库存、订单和消息记录放在一起核对，才能证明链路真的完整。

为什么消息会重复消费

消息系统通常提供至少一次投递语义。消费端处理完成、ACK 丢失或消费者重启，都可能让同一条消息再次出现。解决方向是业务幂等，不是假装消息永远不会重复。

如果 Redis 挂了，秒杀还能继续吗

要看业务设计。可以把秒杀入口降级为不可用，也可以使用数据库条件扣减保证正确性，但吞吐会下降。不能写“Redis 集群保证高可用”却没有故障切换、主从延迟和数据恢复的证据。

项目有没有压测数据

如果没有，就写本地并发验证和结果日志，不写 QPS。压测需要说明机器配置、并发数、数据量、测试工具、成功率和响应时间。没有这些条件，数字没有参考意义。

七天补强清单

  1. 画出登录、缓存、秒杀和 Stream 消费四条链路，标出 Redis Key 和数据库表。
  2. 用多线程脚本验证 Lua 扣减，同时记录重复用户请求和库存变化。
  3. 模拟消费端失败后重启，保留 Pending 列表、重试和 ACK 日志。
  4. 构造缓存删除失败，记录重试和数据库最终状态。
  5. 让锁租期短于业务执行时间，观察重复请求是否被数据库约束拦住。
  6. 整理 stream.orders 的创建、读取、确认和异常处理命令。
  7. 删除“百万并发”“生产集群”“线上事故”等没有证据的描述。
