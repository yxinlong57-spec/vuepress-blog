synchronized 的"锁升级"到底升了什么？直接读对象头看偏向锁、轻量级锁和重量级锁

Loong2026/10/14面经手册Java并发synchronized锁升级大约 8 分钟约 2493 字

环境：Windows 11、OpenJDK 11.0.32.1（Temurin），纯 JDK，用 sun.misc.Unsafe 读对象头，无第三方依赖
运行参数：-XX:BiasedLockingStartupDelay=0（关掉偏向锁的启动延迟，便于立刻观察到偏向状态）
说明：文中每个状态都是本机跑出来的 mark word 原始值。JDK 11 与 JDK 15+ 的默认行为不同，边界在文末单独说明。

先给结论，"锁升级"这个说法哪里不准确

"偏向锁 → 轻量级锁 → 重量级锁，锁会一级一级升级"是面试里的标准说法，但它容易让人误以为这是一条只前进不后退的固定阶梯。实测下来，更准确的说法是：

  • 锁状态由对象头的 mark word 记录，加锁竞争情况决定它停在哪个状态，所谓"升级"是竞争加剧时的状态切换。
  • 偏向一旦被撤销，对象会永久失去"可偏向"能力，直接退回到普通无锁，而不是回到"可偏向"。
  • 轻量级锁在出现真正的阻塞后才会膨胀成重量级锁；只是短时间的多线程竞争，未必会走到重量级。

换句话说，"升级"是一个按竞争强度切换状态的过程，不是一条每次都必然走完的阶梯。下面直接读对象头，把这些状态一个个看过去。

对象头里到底存了什么

HotSpot 在 64 位下的 mark word 是一个 8 字节（64 位）的字，不同状态下复用同一片空间。和锁相关的位在最低几位：

位含义
最低 2 位（lock）00 轻量级锁；01 无锁/偏向；10 重量级锁；11 GC 标记
第 3 位（biased_lock）为 1 且 lock=01 时表示"可偏向/偏向锁"
第 4~7 位（age）对象年龄，用于 GC 分代
其余高位偏向时存线程 ID 与 epoch；存哈希时存 hash

所以只要读出这个字，再解析低 2 位和第 3 位，就能判断当前锁状态。这就是整个实验的核心。

实验：用 Unsafe 读出 mark word 并解码

用 sun.misc.Unsafe 直接读对象偏移 0（mark word 就在偏移 0 处）：

static void dump(String tag, Object o) {
    long m = U.getLong(o, 0L);
    int lock   = (int) (m & 0b11);          // 最低 2 位
    int biased = (int) ((m >> 2) & 1);      // 第 3 位
    int age    = (int) ((m >> 3) & 0xF);
    String state;
    if      (lock == 0b00) state = "轻量级锁 (thin lock)";
    else if (lock == 0b01) state = (biased == 1) ? "可偏向 / 偏向锁" : "普通无锁";
    else if (lock == 0b10) state = "重量级锁 (fat lock)";
    else                   state = "GC 标记";
    System.out.printf("%-20s mark=0x%016X  lock=%d biased=%d age=%d => %s%n",
            tag, m, lock, biased, age, state);
}

Unsafe 是 JDK 内部 API，编译会提示"内部的专有 API，可能会在未来版本删除"，这是预期内的；不想用它可以换 JOL（org.openjdk.jol）库，观察的位完全一样。

现象一：新建对象默认是"可偏向"的

[1] new Object()           mark=0x0000000000000005  lock=1  biased=1  => 可偏向 / 偏向锁

0x5 的二进制最低两位是 01，第 3 位是 1，对应"可偏向"。也就是说，一个刚创建、还没被任何线程锁过的对象，天生就处于"等着被偏向"的状态——这是偏向锁机制的前提。

现象二：单线程加锁，第一次就偏向

[2] 持锁中                 mark=0x000001FD8D299005  lock=1  biased=1  => 可偏向 / 偏向锁
[2] 退出同步块后            mark=0x000001FD8D299005  lock=1  biased=1  => 可偏向 / 偏向锁

同一个对象原来 0x05，加锁后高位出现了一串值（这里是 0x1FD8D2990），这正是持有锁的线程 ID 被写进了 mark word。加锁和解锁都没改低 2 位，因为偏向锁的加锁只是一次 CAS 写入线程 ID，解锁几乎零成本，这就是它在"自始至终只有一个线程访问"时更快的原因。

现象三：第二个线程来抢，偏向被撤销

[3] 线程 B 持锁中          mark=0x00000070C31FF1C8  lock=0  biased=0  => 轻量级锁 (thin lock)
[3] 竞争结束后             mark=0x0000000000000001  lock=1  biased=0  => 普通无锁

第二个线程去拿同一把锁时，JVM 必须撤销偏向（stop-the-world 到安全点检查持有线程是否还活着）。撤销后 biased 变 0，lock 变 00，进入轻量级锁：线程在栈帧里放一个 Lock Record，用 CAS 把 mark word 指向它。这一步不涉及操作系统，是纯用户态的"自旋抢锁"。

注意竞争结束后对象并没有回到"可偏向"，而是停在 普通无锁（biased=0）。偏向被撤销过一次，就再也不会可偏向——这是"锁升级不是单纯阶梯"的第一个证据。

现象四：长时间持锁+阻塞，膨胀为重量级锁

让一个线程持锁 800ms，另一个线程来抢、阻塞等待：

[4] holder 持锁、waiter 阻塞中   mark=0x000001FDB1D69F02  lock=2  biased=0  => 重量级锁 (fat lock)
[4] waiter 终于拿到锁           mark=0x000001FDB1D69F02  lock=2  biased=0  => 重量级锁 (fat lock)

lock=2（0b10）就是重量级锁。轻量级锁靠自旋，适合"锁很快就能拿到"的场景；一旦有线程真的要阻塞等待，JVM 会把对象膨胀成重量级锁，关联一个 ObjectMonitor，靠操作系统的互斥量和等待队列管理线程，代价更高但能正确处理长时间等待。

和我一开始的预期不同：4 个线程各跑 3 次短同步块，观察到的始终是轻量级锁，没有膨胀。"多线程竞争就升重量级"是错的，只有当线程真正进入阻塞（或者自旋超时失败）才会膨胀。这点在写高并发代码时值得记住：能快速拿到锁的临界区，保持短小，就能一直待在廉价的轻量级状态。

现象五：调用 hashCode() 之后，对象再也不能偏向

[5] hashCode()=1025799482  mark=0x0000003D24753A01  lock=1  biased=0  => 普通无锁
[5] 再 synchronized         mark=0x00000070C1DFF540  lock=0  biased=0  => 轻量级锁 (thin lock)

调用 hashCode() 后，哈希值被写进了 mark word 的高位，biased 直接变成 0。原因是偏向锁和哈希值抢同一片空间：偏向锁用高位存线程 ID，普通状态用高位存 hash，二者不能共存。所以对象一旦被调用过 hashCode()（或被放进以 hashCode 为键的集合），就永久不可偏向，加锁直接从轻量级锁开始。

这也是为什么"重写了 hashCode() 又把对象当锁用"的代码，实际上一直在用轻量级/重量级锁，偏生锁优化早就失效了。

版本边界：JDK 15 起偏向锁默认关闭

上面所有"偏向"的现象，在 JDK 15 之后默认就看不到了。JDK 15 通过 JEP 374（Deprecate and Disable Biased Locking） 把偏向锁默认禁用并开始废弃相关参数：

  • JDK 11~14：偏向锁默认开启，-XX:BiasedLockingStartupDelay=0 能立刻观察到偏向。
  • JDK 15+：偏向锁默认关闭，新建对象不再显示"可偏向"，mark word 里也不会再出现偏向线程 ID；要复现偏向得显式打开（在仍保留该参数的版本上）。
  • 相关参数（-XX:+UseBiasedLocking、-XX:BiasedLockingStartupDelay）在后续版本被标记为过时，未来会移除。

所以，"JDK 15 以后，我还需要担心偏向锁撤销的开销吗"这个问题的答案是：默认不用，因为偏向锁压根不启用了。网上大量"锁升级"文章还在讲偏向锁的加锁流程，读的时候要先确认对方说的是哪个 JDK 版本——这是本篇最值得带走的版本意识。

对写业务代码的启示

  • 临界区保持短小。能自旋拿到锁就别让线程阻塞，这样停留在轻量级锁，不触发重量级锁的额外代价。
  • 别把重写过 hashCode 的对象当锁（已经很少见，但也别用字符串常量以外的东西随手当锁）。更本质的建议是：不要用业务对象做锁，用专门的 private final Object 或 ReentrantLock，锁的对象语义清晰、也避免和其他代码意外争用。
  • 锁升级不是性能调优点。绝大多数业务瓶颈不在偏向锁撤销上；先测量再优化，不要为了"避免锁升级"去写复杂代码。
  • 面试里被问到锁升级，答"状态由对象头决定、按竞争切换、JDK 15 起偏向锁默认关闭、不是必然阶梯"，比背一段阶梯图更稳。

小结

  • 锁状态由对象头的 mark word 记录，低 2 位是 lock、第 3 位是 biased_lock；读这个字就能判断状态。
  • 实测状态序列：新建可偏向 → 单线程加锁变偏向 → 第二线程撤销偏向变轻量级锁 → 出现阻塞膨胀为重量级锁。
  • "锁升级"不是固定阶梯：偏向被撤销后不可恢复为可偏向；短竞争未必膨胀为重量级。
  • hashCode() 会占用 mark word 高位，使对象永久不可偏向。
  • 版本边界最重要：JDK 15（JEP 374）起偏向锁默认禁用，新代码不需要再考虑偏向锁的开销。
